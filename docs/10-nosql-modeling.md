# 第10章 NoSQL のデータモデリング

第9章の末尾で確かめたとおり、本書はここまで一貫して、構造はテーブルで持ち、問いは SQL と結合で組み立てるというリレーショナルモデルの前提の上を歩いてきた。
本章で扱う **NoSQL** は、この前提を共有しないデータベース群である。
キーバリュー、ドキュメント、カラムナの三つの型の設計原則を確かめると、どの型にも同じ転換が現れる。
結合を持たない世界では、問いの形に合わせてデータをあらかじめ畳んでおくという第8章の発想が、選択肢の一つではなく設計の出発点になる。
具体例では、開設の近づいた電子書籍ストアを題材に、アプリケーション側のデータストアを設計し、それを分析基盤へ取り込むところまでを行う。

## 概念の解説

### NoSQL の成り立ちと位置づけ

NoSQL は、単一の製品や理論の名前ではない。
リレーショナルモデルと SQL を前提としないデータベース群を緩く束ねた通称であり、範囲の厳密な定義はない[^nosql-name]。
それでも一括りに呼ばれるのは、主要な製品群が同じ事情から生まれ、同じものを手放しているからである。

その事情とは、2000 年代後半のウェブサービスの規模である。
利用者と書き込みの量が単一サーバの RDB で受け止められる限界を超え、データを複数のサーバに分割して持つ（シャーディング）ほかなくなった。
分割した途端、リレーショナルの中心的な道具が高くつくようになる。
結合はサーバをまたぐデータの突き合わせになり、問い合わせのたびに通信が発生する。
トランザクションはサーバをまたぐ合意の手続きになり、書き込みのたびに待ちが発生する。
NoSQL の主要な製品は、この二つを最初から提供しない（または一つのサーバに収まる範囲に限る）ことと引き換えに、分割と複製を素直に行える構造を選んだ[^cap]。

第1章の区別でいえば、NoSQL が受け持つのは OLTP である。
低遅延で読み書きされるアプリケーションのデータストアが主戦場であり、自由な切り口の集計という OLAP の問いには、後述のとおりむしろ弱い。
だからデータエンジニアにとって NoSQL は、まず自分が設計するテーブルとしてではなく、取り込むべき新しい種類のソースとして現れる。
それでも設計原則を知る必要があるのは、集約の境界や履歴の残り方というソース側の設計が、取り込みの設計をそのまま左右するからである。

本章で扱う三つの型は、キーバリュー、ドキュメント、カラムナ（本書では以下ワイドカラムと呼ぶ。名称の整理は後述する）である。
三つは、関連するデータのかたまりを単位として読み書きする点が共通しており、まとめて**集約指向**（aggregate-oriented）と呼ばれる[^aggregate]。
NoSQL にはこのほかにグラフデータベースの系統があるが、集約指向とは設計原則が別であり、本書では扱わない[^graph]。

### 設計原則の転換

リレーショナルの設計は、構造を先に決める。
第2章と第3章で行った手順は、業務の事実を洗い出し、正規化して一度だけ置くことだった。
この置き方は特定の問いを優遇しない。
どの問いも、実行のときに結合で組み立てられるからである。

NoSQL では、この順序が成り立たない。
結合がないから、問いのときに組み立てるという手が使えない[^join-support]。
読みたい形は、あらかじめ作って格納しておくしかない。
そこで設計は、**アクセスパターン**、すなわちアプリケーションがデータに発行する問いの一覧を先に列挙するところから始まる。
そして問いのそれぞれを、一回の取得で返せる形にデータを畳んで置く。
構造が先で問いが後だったリレーショナルに対し、問いが先で構造が後になる。

この「問いの形に畳んで置く」操作自体は、第8章で見たものである。
OBT は結合を済ませた一枚を提供し、ネスト構造は一対多を親の行に畳み込んだ。
ただし、同じ操作の設計上の地位が二つの点で違う。
第一に、第8章の畳み込みは導出だった。
OBT はスタースキーマから作り直せる複製であり、定義の置き場にはしないと確かめた。
NoSQL の畳み込みは一次データそのものであり、作り直す元がない。
第二に、複製の同期の責務が移る。
DWH では、非正規化で生じた複製は変換パイプラインが作り直すことで同期されていた。
NoSQL では、複製した値をそろえ続ける仕事をアプリケーションのコードが負う。
だから NoSQL の設計判断の中心は、何をどこまで複製するか、その同期を誰がいつ行うかに置かれる。

集約指向という共通項は、トランザクションの範囲も定める。
ここでの**集約**とは、常に一緒に読み書きされるデータのかたまり（一つのキーの値、一つの文書、一つのパーティション）を指す。
多くの製品で、原子性の保証は一つの集約の中に限られる。
したがって集約の境界線は、原子的に更新したい範囲が内側に収まるように引く。
カートへの追加でそのカートが壊れないことは保証したいが、二人の顧客のカートをまたぐ原子性は要らない、という要領である。

第1章では、OLTP のモデルは更新異常を防ぐため正規化する方向に設計すると述べた。
NoSQL は OLTP 側でありながら非正規化を既定とするから、この対比と矛盾して見える。
矛盾ではなく、前提が違う。
第1章の対比は結合を使えるリレーショナルの中での話であり、そこでは正規化しても問いに答える能力を失わなかった。
結合を手放した NoSQL では、正規化された構造は問いに答えられない構造になるから、非正規化を受け入れた上で、更新時異常（第3章）の抑え込みをアプリケーションが引き受けるという配分になる。

引き換えに失うものも、畳み込みの性質から決まる。
問いに合わせて畳んだ構造は、畳んでいない問いに弱い。
新しいアクセスパターンが現れたら、新しい畳み込み（テーブルや複製）を足してデータを移し替えるか、全件走査で払うかになる。
リレーショナルとの使い分けの軸はここにある。
問いをあらかじめ列挙し尽くせて、規模か遅延の要件が RDB の限界を超えるなら、NoSQL が合う。
問いが開いているなら（分析はその典型である）、結合で任意の問いに答えられるリレーショナルの中立性が効く。

### キーバリュー

三つの型のうち、最も単純なのがキーバリューである。
キーバリューストアは、キーから値への対応だけを保持する。
操作はキーを指定した格納、取得、削除にほぼ限られ、値の中身をデータベースは解釈しない。
中身に索引も問い合わせも効かないから、値の構造の合意は、読み書きするアプリケーションのコードだけが持つ。

構造の自由度がキーに集中するので、設計はキー設計とほぼ同義になる。
原則は三つある。

- キーは問いの引数から組み立てる。「顧客のカートを取る」という問いなら、顧客の識別子がそのままキーになる。
- 複数の種類のデータが同居するストアでは、キーに種別の接頭辞を付けて（cart#100123 のような連結で）キー空間を仕切る。
- 値には集約を丸ごと入れる。値の部分的な読み書きはできないから、値の単位は、常に一緒に読み書きする単位と一致させる。

適するのは、識別子で引き当てて丸ごと使うデータである。
セッション、カート、キャッシュ、設定値が典型で、いずれも寿命が短いか、失っても復元できるものが多い[^ttl]。
限界も明快で、キー以外の手掛かりでは探せない。
「更新が 30 日ないカートの一覧」のような条件の問いには全件走査しかなく、そういう問いが要件にあるなら、この型の外（別の型、または分析基盤）で答えることになる。

### ドキュメント

ドキュメントデータベースは、キーバリューの値に構造を認めた型である。
値は**文書**、すなわち JSON のような入れ子の構造を持つデータであり、キーバリューと違って、データベースが中身を解釈する。
文書内の項目への索引、条件を付けた問い合わせ、文書の一部だけの更新が効く。

設計の中心は集約の境界の判断、すなわち関連するデータを一つの文書に**埋め込む**か、識別子だけを持って別の文書を**参照する**かである。
判断は次の三つを目安に行う。

- 一緒に読み書きするか。常に親と一緒に取得され一緒に更新されるデータは埋め込む。一回の読みで済み、原子性も文書の中で効く。
- 単独で更新され、共有されるか。複数の文書から使われ、それ自身の都合で更新される事実（マスタ）は参照にする。埋め込むと、更新のたびに埋め込んだ先の全文書を書き換えて回ることになる。
- 際限なく増えるか。上限のない一対多（レビュー、ログ）を埋め込むと文書が育ち続ける。別の文書に切り出す。

実務の設計は、埋め込みと参照の間の折衷に落ちることが多い。
参照にした上で、表示に要る少数の属性（タイトルなど）だけを複製して埋め込む形である。
複製した属性の同期は自分の責務として引き受けることになるが、例外が一つある。
「その時点の値」を写す複製は、そもそも同期してはならない複製である。
注文明細に写した注文時点の単価は、マスタの価格が改定されても書き換えない。
第5章で履歴として扱った時点の事実が、ここでは同期の要らない埋め込みとして現れる。

ドキュメントデータベースはしばしばスキーマレスと呼ばれるが、スキーマが消えたわけではない。
書き込み時にデータベースが構造を検査しなくなった分、構造の合意はアプリケーションのコードに移り、検査は読み出す側で行われる（**schema-on-read**）。
古い構造の文書と新しい構造の文書が混在したとき、どう読み分けるかの管理は、設計の一部として残る。

### ワイドカラム（カラムナ）

三つ目の型は、名称の整理から始める必要がある。
この型はカラムナ、カラム指向、カラムファミリ、ワイドカラムと呼び名が揺れており、特に「カラムナ」「カラム指向」は、第8章の列指向ストレージと同じ語で呼ばれることがある。
両者は別物である。
第8章の列指向ストレージは、表を列ごとに格納するという、分析用データベースの物理配置の話だった。
ここでの型は、行キーの下に多数の列を持ち、行キーの設計で問いに答えるという論理モデルの話である。
本書では、混同を避けて**ワイドカラム**と呼ぶ[^bigtable]。

ワイドカラムのテーブルでは、行を識別するキーが二つの部分からなる。
**パーティションキー**は、行をどのサーバ（パーティション）に置くかを決める。
**クラスタリングキー**は、同じパーティションの中で行を並べる順序を決める。
読み取りの基本形は、パーティションキーで一つのパーティションを引き当て、クラスタリングキーの順で先頭から範囲を読むことである。

設計原則は、この基本形の裏返しである。

- パーティションは一回の取得の単位である。アクセスパターンの「〜の一覧を取る」の「〜」をパーティションキーにする。
- クラスタリングキーは返したい並びである。「直近から N 件」の問いなら、時刻の降順を並びにする。
- テーブルは問いごとに作る。同じデータでも、別の問いには別の並びの別テーブルを用意し、書き込み時に両方へ書く。

読みのたびの組み立てを書き込み時の複製で置き換えるこの配分が成り立つのは、ワイドカラムの実装が追記中心の構造で、書き込みに強いからである[^lsm]。
適するのは、時系列のイベントや行動ログのような、書き込みが激しく、直近の範囲を読む問いが決まっているデータである。

### 分析基盤から見た NoSQL

ここまではアプリケーション側の設計だった。
締めくくりに、視点をデータエンジニアの側へ戻す。

集約指向の畳み込みは、アプリケーションの問いに向けて行われている。
書籍ごとの売上のような自由な切り口の集計は、どの畳み込みにも収まっておらず、答えるには全件走査しかない。
しかもその走査は、低遅延の読み書きを担う本番ストアの負荷になる。
だから NoSQL を採用したシステムでも、分析はこれまでどおり、データを DWH へ運んでから行う。
NoSQL の採用は分析基盤の代替ではなく、分析基盤から見ればソースが一種類増えたことを意味する。

取り込みの設計には、リレーショナルなソースにはなかった仕事が二つ加わる。
一つは構造である。
ソースの単位がテーブルの行ではなく文書やキーの値なので、まず JSON などの半構造化データの列としてロードし、リレーショナルの形に開く変換を基盤側で行う。
第8章で畳むために使ったネストの道具を、今度は開く向きに使うことになる。
もう一つは履歴である。
文書もキーの値も上書きされ、カートのようなデータは削除までされる。
ソースに現在値しか残らないという第5章の問題がそのまま現れるので、定期スナップショットの取得か、変更の流れの購読（第5章の CDC）で変化を拾う。
多くの製品は変更ストリームの機能を備えており、CDC が第一候補になる[^streams]。

## 具体例

第7章から計画されていた電子書籍ストアの開発が、いよいよ始まった。
アプリケーションチームは、ストアのデータストアに NoSQL の採用を検討している。
カートと読書進捗の書き込みが激しく、リリース後の規模の見通しも立てにくいからである。
データチームは、この検討に二つの立場で関わる。
集約の境界と履歴の残り方はデータモデリングの問題そのものだから設計レビューに加わり、同時に、新しいソースの取り込みを設計する。

### アクセスパターンの列挙

アプリチームとの最初の作業は、ER 図を描くことではなく、アクセスパターンを列挙することである。
主要な問いは次のとおりだった。

| 問い | 発行者 | 頻度 |
| --- | --- | --- |
| 顧客のカートを取得し、更新する | ストア画面 | 高 |
| 注文を確定し、注文の内容を表示する | ストア画面 | 中 |
| 読書位置を記録し、端末間で同期する | 閲覧アプリ | 最高 |
| 書籍ごと、日ごとの売上を集計する | データチーム | 日次 |
| 更新が 30 日ないカートの一覧を出す | マーケティング | 週次 |

表を見た時点で、仕分けが一つできる。
下の二つ（売上の集計と放置カートの一覧）は、識別子で引き当てる問いではなく、条件と切り口の問いである。
本番ストアの畳み込みで答える問いではないから、分析基盤の仕事として取り込みの節まで預ける。
残った三つを、それぞれに合う型へ割り当てていく。

### カートのキー設計

カートは、顧客がストアを開くたびに読まれ、商品を出し入れするたびに書き換わる。
明細の一部だけを読む問いはなく、常に丸ごと読んで丸ごと描画するから、カート全体を一つの集約としてキーバリューに置く。

```text
キー: cart#100123
値:
{
  "updated_at": "2026-08-01T09:12:45Z",
  "items": [
    {"isbn": "9784XXXXXXXX1", "title": "データモデリング入門", "unit_price": 1540, "quantity": 2},
    {"isbn": "9784XXXXXXXX2", "title": "分析基盤の設計", "unit_price": 3080, "quantity": 1}
  ]
}
```

キーは、問いの引数である顧客 ID から組み立て、セッションなど他の種類のキーと同居しても衝突しないよう cart# の接頭辞で仕切る。
値にはタイトルと単価を複製している。
カートの描画のたびに書籍マスタへ問い合わせないための複製であり、価格改定との食い違いは、注文確定の時点で最新の価格を検証し直すという業務の手続きで吸収する。
複製の同期を、常時の同期ではなく確定時の検証一回に落とした形である。

### 注文文書の埋め込みと参照

注文の確定では明細と支払いの情報が原子的に書かれ、注文の表示では常に全体が読まれる。
注文一件を一つの文書として、ドキュメントデータベースに置く。

```json
{
  "order_id": "E2026-000042",
  "customer_id": 100123,
  "ordered_at": "2026-08-01T09:15:02Z",
  "payment": {"method": "credit_card", "total_amount": 6160},
  "items": [
    {"isbn": "9784XXXXXXXX1", "title": "データモデリング入門", "unit_price": 1540, "quantity": 2},
    {"isbn": "9784XXXXXXXX2", "title": "分析基盤の設計", "unit_price": 3080, "quantity": 1}
  ]
}
```

集約の境界は、概念の解説の三つの目安のとおりに割れる。
明細は埋め込む。
常に注文と一緒に読み書きされ、確定後は増えも変わりもしないからである。
埋め込んだタイトルと単価は注文時点の値を保存する複製であり、書籍マスタが改定されても書き換えない。
マスタが上書き型でも注文の中に時点の事実が残るという意味で、この複製は第5章の履歴の役目を兼ねている。
一方、顧客は customer_id の参照にとどめる。
氏名は注文時点の事実として残したい情報ではなく、現在のプロフィールとして表示したい情報だからである。
埋め込んでしまうと、改名のたびに過去の注文文書を書き換えて回るか、古い氏名を表示し続けるかの二択を引き受けることになる。

### 読書進捗のテーブル設計

読書位置の同期は、書き込みの最も激しい問いである。
ページがめくられるたびに端末が位置を送り、別の端末で開かれた瞬間に最新の位置を返す必要がある。
時系列のイベントを積んで直近を読む形なので、ワイドカラムに置く。

```sql
-- 擬似 DDL（CQL 相当の構文で書く）[^cql]
CREATE TABLE reading_progress (
    customer_id BIGINT,
    isbn        CHAR(13),
    event_time  TIMESTAMP,
    position    TEXT,
    device_id   TEXT,
    PRIMARY KEY ((customer_id, isbn), event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);
```

パーティションキーは customer_id と isbn の組である。
「この顧客のこの書籍の最新位置」という問いの引数がそのまま組になっており、最新位置はパーティションの先頭 1 行を読むだけで返る。
クラスタリングキーの event_time を降順にしてあるから、読む範囲を伸ばせば「この書籍の読書履歴を新しい順に」も同じテーブルで返る[^partition-growth]。

ここで、閲覧アプリの要件がもう一つ現れたとしよう。
ライブラリ画面に、購入済みの書籍を最近読んだ順に並べたい。
reading_progress はこの問いに答えられない。
パーティションが顧客と書籍の組で切られているから、顧客の書籍横断の並びはパーティションをまたいでしまう。
ワイドカラムの流儀は、この問いのための別テーブル（customer_id だけをパーティションキーにし、最終閲覧時刻の降順を並びに持つ一枚）を作り、進捗の書き込み時に両方へ書くことである。
読みの単純さを書き込みの複製で買う、テーブルは問いごとという原則の実際の姿がこれである。

### 分析基盤への取り込み

ストアの開設後、データ基盤にはソース ebook が加わり、shop、wms、pos と合わせて四つになる。
預けてあった二つの問いに、ここで答える。

売上の集計は、注文文書の取り込みで答える。
注文文書は、ドキュメントデータベースの変更ストリームから日次で DWH の生テーブルへ積む。
文書 1 件が 1 行、中身は JSON 型の 1 列である[^variant]。
staging の規約（第9章）はここでも変えない。
stg_ebook_orders は文書 1 件を 1 行のまま、列への型付けと改名だけを行う写しとする。
明細への展開は行数を変える操作だから、staging ではなく intermediate に置く。

```sql
-- models/staging/ebook/stg_ebook_orders.sql
SELECT
    JSON_VALUE(doc, '$.order_id')                       AS order_id,
    CAST(JSON_VALUE(doc, '$.customer_id') AS BIGINT)    AS customer_id,
    CAST(JSON_VALUE(doc, '$.ordered_at') AS TIMESTAMP)  AS ordered_at,
    JSON_QUERY_ARRAY(doc, '$.items')                    AS items
FROM {{ source('ebook', 'orders') }}
```

```sql
-- models/intermediate/int_ebook_order_items.sql
SELECT
    o.order_id,
    o.customer_id,
    o.ordered_at,
    JSON_VALUE(item, '$.isbn')                          AS isbn,
    JSON_VALUE(item, '$.title')                         AS title_at_order,
    CAST(JSON_VALUE(item, '$.unit_price') AS NUMERIC)   AS unit_price,
    CAST(JSON_VALUE(item, '$.quantity') AS BIGINT)      AS quantity
FROM {{ ref('stg_ebook_orders') }} AS o
CROSS JOIN UNNEST(o.items) AS item
```

第8章で著者の配列を畳むのに使った道具（構造体の配列と UNNEST）が、ここでは文書を明細の行に開く向きで働いている。
この先は、もう新しい話ではない。
書籍のビジネスキーは ISBN と決めてあり（第2章、第7章）、統合層には hub_books が立っている。
電子書籍の注文は、第7章で予告したとおり Hub と Link と Satellite を足して統合層に収め、マートの売上ファクトへ流す。
指標の側では、「オンライン売上に電子書籍を含むか」という第9章と同型の食い違いが起きる前に、ebook_revenue を宣言し、全社売上 total_revenue の派生の式にこれを加えて定義を更新する。

放置カートの問いには、履歴の取り込みが要る。
カートは上書きされ、注文の確定や取りやめで削除されるから、どの時点にどんなカートが存在したかという事実は、本番ストアには残らない。
そこでカートは変更ストリームから取り込み、キーごとの版を追記で積む。
第5章の snapshot が定期取得と比較で組み立てていた有効期間の形を、今度は届いた変更イベントと削除イベントから組み立てる形である。
最新の版の更新時刻が 30 日より古く、削除イベントの届いていないキーを選べば、放置カートの一覧になる。
なお読書進捗は、ソース自体が追記のイベントなので、そのまま積めばよい。

本章で、本書の道具は出そろった。
リレーショナルの正規化に始まり、ディメンショナルモデリング、履歴、統合層、畳み込み、規約と宣言、そして結合を持たない世界の設計まで、どれも「この決定をどこに置くか」への答えとして学んできた。
第11章は総合演習である。
題材のドメインを一つ決め、概念モデルから物理モデルまでを通しで設計し、各章の判断を一つの設計の中で組み合わせて使う。

## 参考文献

- Pramod J. Sadalage, Martin Fowler, *NoSQL Distilled: A Brief Guide to the Emerging World of Polyglot Persistence*, Addison-Wesley, 2012.（集約指向という整理の出典。型ごとの特徴と使い分けを短くまとめた入門）
- Martin Kleppmann, *Designing Data-Intensive Applications*, O'Reilly Media, 2017.（データモデルと問い合わせ言語、分散、レプリケーションまで。本章の背景全般を支える定番）
- MongoDB, "Data Modeling", MongoDB Manual. https://www.mongodb.com/docs/manual/data-modeling/ （埋め込みと参照の判断基準の一次資料）
- AWS, "Best practices for designing and architecting with DynamoDB", Amazon DynamoDB Developer Guide. https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/best-practices.html （アクセスパターン駆動のキー設計の一次資料）
- Fay Chang et al., "Bigtable: A Distributed Storage System for Structured Data", OSDI, 2006. https://research.google/pubs/bigtable-a-distributed-storage-system-for-structured-data/ （ワイドカラムの原型となった論文）

[^nosql-name]: 2009 年に分散データストアの勉強会の名前として使われて広まった。「SQL を使わない」ではなく "not only SQL" と読み替える説明が定着しているが、いずれにせよ厳密な定義を持つ術語ではない。

[^cap]: 分散したデータベースが、ネットワークの分断時に一貫性と可用性を両立できないことは CAP 定理として知られる。NoSQL の多くは、複製間の一時的な食い違いを許して可用性を取り、時間とともに収束させる結果整合性を採る。本書の主題であるモデリングからは外れるので、これ以上は立ち入らない。

[^join-support]: 「結合がない」は概ねの整理である。ドキュメントデータベースには結合の演算を持つ製品もあるが、分散配置のもとでは制約と代償が大きく、設計の前提には置かないのが通例である。

[^aggregate]: 集約という語はドメイン駆動設計（DDD）の aggregate に由来する。キーバリュー、ドキュメント、カラムファミリの三者を集約指向とまとめる整理は、参考文献に挙げた Sadalage と Fowler による。

[^graph]: グラフデータベースは、頂点と辺のつながりを何段でも辿る問いに特化した型で、集約に畳むどころか、関係を細かく持って探索する方向の設計になる。SNS のつながりや経路の分析が典型の用途である。

[^ttl]: 多くのキーバリューストアは、キーごとに生存時間（TTL）を設定して、期限の切れたデータを自動で消せる。セッションやカートの掃除はこの機能に任せることが多い。

[^bigtable]: この型の原型は Google の Bigtable（参考文献の論文）であり、HBase と Cassandra がその系譜にある。DynamoDB のパーティションキーとソートキーも同じ二部構成である。なお、複数の種類の集約を一つのテーブルのキー空間に同居させる DynamoDB の流儀は、シングルテーブル設計と呼ばれる。

[^lsm]: 代表的な実装は LSM ツリー（Log-Structured Merge-tree）である。書き込みをメモリ上の構造とファイルへの追記で受け、後段で整列済みのファイルを併合することで、ランダムな書き込みを順次書き込みに変える。

[^cql]: 構文は Cassandra の CQL に倣った。PRIMARY KEY の内側の括弧がパーティションキー、残りがクラスタリングキーである。製品によって語彙は違うが（DynamoDB ではパーティションキーとソートキー）、二部構成のキーで配置と並びを決める設計は共通する。

[^partition-growth]: パーティションは無限に育てないのが定石である。イベントが積もり続けるテーブルでは、月をパーティションキーに含めて期間で切る、TTL で古い行を消すといった手当てを合わせて行う。

[^variant]: 半構造化データ用の型は、BigQuery では JSON 型、Snowflake では VARIANT が相当する。本文の JSON_VALUE と JSON_QUERY_ARRAY は BigQuery の構文で、Snowflake では doc:order_id::STRING のようなパス記法が相当する。

[^streams]: 例えば MongoDB の Change Streams、DynamoDB Streams、Cassandra の CDC 機能がこれに当たる。
