# 第7章 演習問題

対象章：[第7章 Data Vault](../07-data-vault.md)（[読み上げ原稿](../audio-scripts/07-data-vault.md)）

## 問題

### 問1

Data Vault では、統合層への取り込みの時点で適用してよい変換と、後段まで遅らせる変換を区別する。
取り込みの時点で適用してよい変換はどれか。

- A. 同じ書籍について食い違う値を届けた複数のソースのうち、どれを正とするかの解決
- B. 文字コードや空白の整形、型の統一といった、値の意味を変えない変換
- C. 別々のシステムに現れた二つの顧客記録を同一人物とみなす突き合わせ
- D. 売上合計のような計算済み指標の作り置き

### 問2

Data Vault は、どのソースから届いた事実も Hub、Link、Satellite の三種類のテーブルに分解して格納する。
この分解で三種類を切り分ける基準は何か。

- A. データ量の大小で、行数の多い部分を専用のテーブルに隔離する
- B. 参照頻度で、よく読まれる部分を結合の少ない形に寄せる
- C. 正規形の次数で、第3正規形を満たす部分とそうでない部分を分ける
- D. 変わりにくさで、最も安定したビジネスキーと、変わりうる関係、頻繁に変わる記述を分ける

### 問3

Link は、実際の業務では 1 注文に 1 会員しか結びつかない場合でも、キーの組を常に多対多の形で持つ。
この設計の狙いはどれか。

- A. 結合するテーブル数が減り、問い合わせが速くなる
- B. 正規化の原則が、関係を独立したテーブルに切り出すことを要求している
- C. 業務の結び方が変わっても、テーブル構造を変えずに行の追加だけで受け止められる
- D. ハッシュキーを主キーに使う以上、1 対多の制約はそもそも表現できない

### 問4

Satellite は記述属性の履歴を持つが、有効期間の終端を表す valid_to 列を持たない。
その理由はどれか。

- A. 終端を書き込むには前の行の更新が必要になり、追記だけで運用する規則が破れるから
- B. 終端の列を持たないことで、履歴テーブルの容量を抑えられるから
- C. 終端は保存するより問い合わせ時に計算するほうが速いから
- D. hashdiff 列が変更の検出と終端の記録を兼ねているから

### 問5

Data Vault はテーブル数と結合数が第3正規形のモデルの数倍になる代償を伴う。
この代償を払ってでも採用する根拠になる状況はどれか。

- A. ソースが少なく安定しており、統合層の構築コストを最小にしたい
- B. 利用者が参照する分析用テーブルの結合を減らし、問い合わせを速くしたい
- C. スタースキーマを置き換えて、利用者に統合層を直接見せたい
- D. ソースの追加が今後も続き、レポートの数字をソースに記録された値まで遡って説明する要件がある

## 解答と解説

### 問1

**解答**：B

章の「事実の保存と解釈の分離」で述べたとおり、入り口で適用してよいのは値の意味を変えない変換（hard rule）だけである。
A と C はどちらも意味を選ぶ変換（soft rule）であり、入り口で適用すると判断前にソースが届けた値が残らず、規則を変えたときの再統合や監査の要件に応えられなくなる。
D の計算済み指標も soft rule の適用結果であり、置くなら Raw Vault ではなく Business Vault の仕事である。

### 問2

**解答**：D

章の「三種類のテーブルへの分解」で述べたとおり、分解の軸は変わりにくさである。
最も安定したビジネスキーを Hub に、業務の進め方とともに変わる関係を Link に、最も頻繁に変わる記述を Satellite に置く。
安定したものと変わりやすいものを同居させないから、ソースの追加や変更を、変わりやすい部品への追記と新しい部品の追加だけで受け止められる。
A と B のような物理的な性能の都合や、C のような正規形の次数は、この分解の基準ではない。

### 問3

**解答**：C

今の業務の制約（1 注文 1 会員）をテーブル構造に焼き込むと、法人契約で複数の担当者が紐づくようになったときなどに構造の改修が要る。
組を行として持つ形なら、新しい結び方は行が増えるだけで受け止められる。
これは事実の形を業務の制約どおりに固定する正規化とは逆の選択であり、B は方向を取り違えている。
制約の検査と表現は捨てられるのではなく、下流のマートに任される。

### 問4

**解答**：A

Vault は追記だけで運用し、更新と削除を行わない。
valid_to を持つと、行の終端を書き込むために前の行の更新が要り、この規則が破れる。
終端は問い合わせの時点で次の行の load_ts から導けばよく、章の具体例では LEAD を使って第5章と同じ半開区間の形を導出していた。
B や C のような容量と速度の都合が理由ではなく、D の hashdiff は変更検出のための列であって終端の情報は持たない。

### 問5

**解答**：D

章の「採用の判断」で述べたとおり、分解の物量が見合うのは変化と監査の要件が重いときである。
拡張が「足すだけ」に固定される価値はソースが追加されるたびに効き、soft rule 適用前の事実が残る構造が、数字をソースの記録まで遡る監査の要件に応える。
A の状況では分解の物量だけを払うことになり、第6章の具体例が統合層を立てなかった判断と同じく、採用しないのが妥当である。
B と C は利用者に見せる層の話であり、Data Vault はスタースキーマと競合せず、統合層の席に座るモデリング法である。
