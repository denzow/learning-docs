# 第4章 演習問題

対象章：[第4章 ディメンショナルモデリング](../04-dimensional-modeling.md)（[読み上げ原稿](../audio-scripts/04-dimensional-modeling.md)）

## 問題

### 問1

Kimball の設計プロセスでは、グレインの宣言がディメンションの識別とファクトの識別より前に置かれている。
この順序になっている理由として適切なものはどれか。

- A. 原子的グレインで行数を見積もれば、必要なストレージ構成を設計の初期に確定できるから
- B. 1 行が何を表すかが決まってはじめて、ある記述がその行について一意か、ある数値がその粒度と整合するかを判定できるから
- C. グレインが決まらないと、測定対象とするビジネスプロセスを選べないから
- D. グレインを宣言しておけば、BI ツールが問い合わせを自動で組み立てられるようになるから

### 問2

分析者から「書籍ごとの平均販売単価を知りたい」という要望が届いた。
ファクトテーブルの設計として適切な対応はどれか。

- A. 明細ごとの単価をメジャーとして持ち、問い合わせでは単価の平均を取る
- B. 書籍ごとの平均単価を変換処理で事前計算し、ファクトテーブルの列として持つ
- C. 平均単価は書籍を説明する値なので、書籍ディメンションの属性として持つ
- D. 金額と数量を加法的なメジャーとして持ち、問い合わせで金額の合計を数量の合計で割る

### 問3

ディメンションを正規化して枝分かれさせるスノーフレークスキーマを、Kimball は推奨しない。
その理由として適切なものはどれか。

- A. ディメンションはファクトに比べて行数が小さく、正規化で節約できる容量がわずかな一方、結合の段数と分析者が把握すべきテーブルの数が増えるから
- B. 正規化されたディメンションでは、属性の変更を履歴として残せなくなるから
- C. ディメンションを正規化すると更新時異常が発生し、データの整合性が保てなくなるから
- D. 枝分かれしたディメンションの結合には、BI ツールが対応していないから

### 問4

Kimball の設計でディメンションテーブルの主キーにサロゲートキーが必要になるのは、どんなときか。

- A. スタースキーマを構成するすべてのディメンションで、例外なく必要になる
- B. ファクトテーブルの行を一意に特定する必要があるとき
- C. 属性の変更を上書きせず、変更前と変更後を別々の行として残すとき
- D. ディメンションをさらに正規化して、参照先のテーブルを切り出すとき

### 問5

年や月や曜日は日付関数で計算できるにもかかわらず、日付ディメンションをテーブルとして持つ。
その価値の説明として適切なものはどれか。

- A. 祝日や営業日、会計年度の四半期のような、カレンダーという業務知識に属していて計算では導けない属性を持てるから
- B. 年や月の抽出計算を省けるので、問い合わせの実行が大幅に速くなるから
- C. 日付ごとに 1 行を持つことで、ファクトテーブルのグレインの一意性を保証できるから
- D. 日付の表記の揺れをディメンション側で吸収し、ソースシステムごとの形式差を隠せるから

## 解答と解説

### 問1

**解答**：B

ディメンションの識別は「グレインの 1 行について値が一意に決まるか」、ファクトの識別は「グレインと整合するか」という判定であり、どちらも 1 行が何かが確定していなければ下せない。
本章の具体例では、共著の書籍で「著者」が明細 1 行について一意に決まらないと分かるのが、グレインを先に宣言した効果だった。
C は手順の順序が逆で、ビジネスプロセスの選択はグレインの宣言より前にある。
D は宣言の順序ではなくスタースキーマという配置の利点であり、根拠が別である。

### 問2

**解答**：D

単価や比率のような非加法的な値は、そのまま集計せず、分子と分母を加法的なメジャーとして持ち、問い合わせの側で割って求める。
A の単価の平均は、数量の多い明細も少ない明細も同じ重みで数えてしまうため、金額の合計を数量の合計で割った値と一致しない。
B や C のように割った結果を事前に持つと、期間や顧客など別の切り口で区切り直した平均を求められなくなる。
加法性の三分類の話題に対応する。

### 問3

**解答**：A

ファクトが数億行に育つのに対しディメンションは数万から数十万行にとどまるという非対称があるため、ディメンションを正規化しても容量の節約はわずかで、結合と把握すべきテーブルが増える不利だけが残る。
C は OLTP 側で正規化を支える論理だが、ディメンションテーブルは変換処理だけが書き込み、読み取り専用で使われるため、更新時異常の心配は当たらない。
B の履歴の可否は正規化とは別の問題で、Slowly Changing Dimensions の話題である。
スタースキーマとスノーフレークスキーマの対比に対応する。

### 問4

**解答**：C

変更前と変更後を別々の行として残すと、同じソース ID を持つ行が複数でき、ソースの ID では行を特定できなくなるため、DWH 側で振り直したキーが必要になる。
A は誤りで、常に現在値で上書きするディメンションならソースの ID をキーに使って差し支えなく、本章の具体例もそうしている。
B はファクト側の話で、明細を特定するのは order_id と line_no のような縮退ディメンションの役割である。
ディメンションのサロゲートキーの節に対応し、履歴の持ち方そのものは第5章の Slowly Changing Dimensions で扱われる。

### 問5

**解答**：A

祝日かどうか、営業日かどうか、会計年度のどの四半期かは、日付そのものからは計算で導けないカレンダーの業務知識であり、テーブルとして持つほかない。
具体例でも、祝日一覧の CSV を結合して is_holiday を用意したおかげで、問い合わせには祝日の一覧も日付の計算も現れなかった。
B は誤りで、計算できる属性を列にするのは主目的ではなく、10 年分でも 4,000 行に満たない小さなテーブルなので性能の議論でもない。
C のグレインの一意性はファクトテーブル側の検査で担保するものである。
