# 第5章 演習問題

対象章：[第5章 Slowly Changing Dimensions](../05-slowly-changing-dimensions.md)（[読み上げ原稿](../audio-scripts/05-slowly-changing-dimensions.md)）

## 問題

### 問1

顧客ディメンションに氏名、メールアドレス、会員ランクの属性がある。
これらに SCD のタイプを割り当てるときの考え方として適切なものはどれか。

- A. ディメンションのテーブルごとに一つのタイプを選び、全属性に同じ方式を適用する
- B. 属性ごとに、その属性へどんな問いが届くかを基準にタイプを選び、一つのテーブルの中で方式が混在してよい
- C. ソースシステムでの更新頻度が高い属性から順に Type 2 を割り当てる
- D. 将来どんな問いが届くかは予測できないため、すべての属性を履歴の残る Type 2 にそろえる

### 問2

ある属性を Type 1（上書き）で管理すると決めた。
当時の値を問う問いが想定されない属性であっても残る注意点はどれか。

- A. 変更のたびに行が追加され、ディメンションの容量が増え続ける
- B. サロゲートキーが振り直され、ファクトからの参照が壊れる
- C. 有効期間の重複により、集計でファクトの行が複製される
- D. 過去に作った集計を同じ SQL で再実行すると、その間の変更の分だけ数字が変わる

### 問3

Type 2 ディメンションを使った「注文当時の会員ランク別の売上」の集計では、問い合わせの SQL に有効期間の条件が現れない。
その理由として正しいものはどれか。

- A. ファクトのロード時に注文時刻で有効な版を照合し、そのサロゲートキーを外部キーとして書き込んであるため、問い合わせは等値結合だけで済むから
- B. is_current が真の行だけに絞って結合すれば、注文当時の値が自動的に選ばれるから
- C. データベースが valid_from と valid_to の列を認識し、結合時に期間を自動で解決するから
- D. 自然キー（customer_id）で結合すると、最も古い版が優先して選ばれるから

### 問4

行の追加（Type 2）ではなく列の追加（Type 3）が適しているのは、どのような変更への対応か。

- A. 顧客ごとに異なる時期に繰り返し起きる変更で、そのすべての履歴を残したい場合
- B. 誤入力の訂正のように、古い値を残す価値がない変更
- C. 営業テリトリーの再編のように全体で一斉に一度だけ起きる変更で、全期間を新旧どちらの体系でも集計したい場合
- D. slowly と呼べないほど頻繁に起きる変更で、行の増加を抑えたい場合

### 問5

ソースが現在値しか持たないため、日次実行の dbt snapshot で顧客の履歴を蓄積することにした。
この設計が抱える限界として正しいものはどれか。

- A. check_cols に指定しなかった属性が変わったときにも、不要な版が追加されてしまう
- B. 運用を始める前に起きた変更は復元できず、同じ日のうちに複数回起きた変更は中間の値が失われる
- C. 実行のたびにサロゲートキーの値が変わり、ファクト側の参照を張り直す必要がある
- D. 版が増えるほど比較の対象が増え、実行時間が過去の変更の回数に比例して伸びる

## 解答と解説

### 問1

**解答**：B

タイプを選ぶ単位はテーブルではなく属性であり、基準はその属性に当時の値を問う問いが届くかである。
同じ顧客ディメンションでも、会員ランクは Type 2、メールアドレスは Type 1 という混在が普通の姿になる。
D は表現力の面では成り立つが、運用の仕事が増え、誰も問わない履歴がノイズとしてすべての問い合わせに付いて回るため、実務の均衡点にならない。
「ディメンションの変更という問題」と「タイプの使い分け」の節に対応する。

### 問2

**解答**：D

Type 1 が失うのは過去の値だけでなく、過去に作った集計の再現性も失われる。
先月作ったレポートを今月同じ SQL で再実行すると、上書きされた顧客の分だけ数字が動き、利用者にはデータの誤りと区別が付かないため、仕様として説明できるようにしておく必要がある。
A と C は行を追加する Type 2 で問題になる事柄であり、行を書き換えるだけの Type 1 では起きない。
「Type 1（上書き）と Type 0（保持）」の節に対応する。

### 問3

**解答**：A

期間の照合はファクトのロード時に一度だけ行い、出来事の時点で有効だった版のサロゲートキーをファクトに書き込む。
問い合わせではそのキーの等値結合だけで当時の値が付くため、期間条件も日付の計算も現れない。
B の is_current で絞って結合すると付くのは現在の値であり、当時の値を問う集計には答えられない。
「Type 2（行の追加）」の節と、具体例のファクトへのサロゲートキーの割り当てに対応する。

### 問4

**解答**：C

Type 3 は現在値の列に加えて以前の値の列を並べて持ち、同じ期間を新旧両方の切り口で集計する問いに答える。
Type 2 は行が期間で分かれるため、この問いには答えられない。
A は変更のたびに列を増やすわけにいかないため Type 3 が向かない典型であり、B は Type 1、D は Type 4（ミニディメンション）の受け持ちである。
「Type 3（列の追加）」と「Type 4 以降」の節に対応する。

### 問5

**解答**：B

定期取得と比較による変更検出には、運用開始以前の履歴を遡れないことと、取得の間隔より細かい変化を捉えられないことという二つの限界がある。
章の具体例では、前者には最初の版の valid_from を過去側の番兵値へ開く手当てを施し、後者は日単位で捉えられれば問いに足りると判断した。
A は逆で、check_cols に指定した列の変更だけが版を増やす。
C はハッシュ方式の採番なら同じ入力から同じキーが再現されるため起きない。
「タイプの使い分けと変更の検出」の節と、具体例の snapshot の限界の記述に対応する。
