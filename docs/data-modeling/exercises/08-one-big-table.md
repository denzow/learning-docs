# 第8章 演習問題

対象章：[第8章 ワイドテーブルと One Big Table](../08-one-big-table.md)（[読み上げ原稿](../audio-scripts/08-one-big-table.md)）

## 問題

### 問1

行指向の OLTP では「複製は高く、結合で導く方が安い」という損得が成り立っていたが、列指向のクラウド DWH ではこれが反転した。
反転の説明として適切なものはどれか。

- A. 列指向では問い合わせのたびに全列がまとめて読み込まれるため、複製で列が増えても読み取りの量が変わらないから
- B. 値の種類が少ない列は辞書圧縮などで縮み、明細への複製がほとんど膨らまない一方、結合に伴うシャッフルの費用は行数に応じて掛かり続けるから
- C. クラウド DWH のストレージ形式が更新の異常を防ぐ仕組みを備えており、複製の書き込み側の危険がなくなったから
- D. ストレージの単価が下がったことで、保存するデータ量の増減が費用にほとんど影響しなくなったから

### 問2

One Big Table（OBT）の説明として適切なものはどれか。

- A. 複数のビジネスプロセスのファクトを統合し、全社の問いに一枚で答えられるようにしたテーブル
- B. グレインを粗くしてディメンションの組み合わせごとの集計値を事前計算し、行数を抑えたテーブル
- C. スタースキーマを置き換えるモデリング法であり、marts 層のモデルはこの形で設計する
- D. 一つのビジネスプロセスのファクトについて、グレインを保ったまま参照するディメンションの属性を畳み込んだ、スタースキーマから導出する一枚

### 問3

共著の書籍のように、明細 1 行に複数の著者が対応する一対多の関係を OBT に持たせたい。
グレインを保ちつつ著者単位の集計にも答えられる方法はどれか。

- A. 著者の構造体の配列を明細の 1 列として格納し、著者単位の集計では読み出し時に配列を行に展開してから集約する
- B. 著者のテーブルを平らに結合して明細の行を著者の数だけ持たせ、集計時に重複を取り除く
- C. 著者名を連結した文字列と著者数の列に要約して持たせる
- D. 著者の情報は OBT に含めず、対応表を別のテーブルとして提供して利用者に結合してもらう

### 問4

OBT はスタースキーマからの導出にとどめ、ソースから直接組んで指標の定義をその変換に書くことは避けるとされる。
その理由として適切なものはどれか。

- A. ソースから直接組むと列のデータ型が揃わず、列指向の圧縮が効かなくなるから
- B. スタースキーマを経由しない変換は、経由する変換より再構築の計算費が大きくなるから
- C. 提供する一枚が増えるたびに定義の複製が増え、一枚ごとに数字の食い違うサイロが提供層で再現されるから
- D. ファクトテーブルとの行数の照合ができなくなり、グレインの検査が書けなくなるから

### 問5

スタースキーマと OBT の使い分けとして適切なものはどれか。

- A. OBT の方が問い合わせが常に速いので、BI ツールを含むすべての提供先を OBT に移行する
- B. 定型のダッシュボードや設計の知識を前提にできない利用者、一枚の表を要する道具には OBT を見せ、結合を書ける分析者の探索にはスタースキーマを残して併存させる
- C. 探索的な分析には結合を省ける OBT が向き、問いが固定される定型のダッシュボードにはスタースキーマが向く
- D. スタースキーマは OBT を作るまでの中間形であり、必要な OBT が揃った時点で提供を止めてよい

## 解答と解説

### 問1

**解答**：B

列指向は同じ列の値をまとめて格納するため、書名のような値の種類が少ない列を数億行に複製しても、辞書と参照の並びに縮んでほとんど膨らまない。
一方、結合が伴うシャッフル（結合キーごとの行の再配置）の費用は圧縮では消えず、行数に応じて残るため、複製を一度作る側が相対的に安くなった。
A は逆で、列指向では参照しない列は読まれない。
C は列指向の効果ではなく、複製の書き込み側の危険は「変換処理だけが書き込み、読み取り専用で使う」という第3章の判断基準が抑えていた。

### 問2

**解答**：D

OBT は一つのプロセスのファクトのグレインを変えずに、参照するすべてのディメンションの属性を畳み込んだ一枚であり、スタースキーマから導出する。
A は名前からの誤解で、OBT はグレイン一つにつき一枚であり、プロセスをまたぐ問いにはドリルアクロスが要る。
B はグレインを粗くする方向の事前計算であり、OLAP キューブや集計済みテーブルの説明にあたる。
C は本章が繰り返し否定する理解で、OBT はスタースキーマを置き換えるのではなく、そこから写す提供の形である。

### 問3

**解答**：A

クラウド DWH の配列と構造体の型を使えば、著者の構造体の配列を明細 1 行の中に 1 列として畳み込め、行数は変わらず多側の情報も失われない。
集計時に UNNEST などで配列を行に開けば、著者単位の問いにも答えられる。
B は平らな結合で行が著者の数だけ複製され、「注文明細 1 行」というグレインの宣言が壊れる。
C は第4章の妥協であり連結文字列からは著者を取り出せず、D は結合を利用者に返してしまい、結合を済ませた一枚を提供するという OBT の目的に反する。

### 問4

**解答**：C

指標の定義や読み替えのロジックを OBT ごとの変換に書くと、一枚増えるたびに定義が複製され、ダッシュボードごとに数字の食い違う独立データマートのサイロ（第6章）が提供層で再演される。
これを防ぐため、定義はスタースキーマの側に一度だけ置き、OBT はそれを平らに写すだけの層にする。
A と B のような物理的な性能の問題ではなく、本章が三つ目の代償として挙げた、定義の置き場という構成の問題である。
D の検査は導出の正しさを見張る手段であって、導出にとどめる理由そのものではない。

### 問5

**解答**：B

OBT が見合うのは、設計の知識を前提にできない提供先、同じ結合を高頻度で繰り返す定型のダッシュボード、一枚の表を要求する道具に渡す場面である。
一方、OBT は畳み込んだ時点の切り口に問いを固定するため、結合を書ける分析者の探索にはどの属性でも後から組み合わせられるスタースキーマが柔らかく、両者は置き換えではなく併存になる。
C はこの向き不向きが逆である。
A と D は「スタースキーマを OBT で置き換える」という理解であり、定義を一箇所に置く層としてスタースキーマを残す本章の構成と合わない。
