# 第11章 総合演習（読み上げ原稿）

対象章：[第11章 総合演習](../11-capstone.md)

第11章、総合演習。この章では、新しい技法は導入しません。その代わりに、題材のドメインを一つ決めて、概念モデルから物理モデルまでを通しで設計し、これまでの章で学んだ判断を一つの設計の中で組み合わせて使います。題材には、ここまで使ってきた書籍オンラインストアではなく、フィットネスクラブチェーンを選びます。慣れた題材をあえて手放すのは、各章の判断が書籍という題材の性質にではなく、業務と問いの形に結びついていることを、別のドメインの上で確かめるためです。

本題に入る前に、通しの設計で判断が現れる順序を整理しておきます。これまでの章では、技法を一つずつ、それが解く問題と対にして学んできました。通しの設計では、同じ判断が互いに依存し合いながら、おおむね決まった順序で現れます。設計の入力は二種類あります。業務の構造と、届いている問いです。OLTP 側の設計は業務の構造から導かれます。テーブルの分解を決める関数従属は、業務ルールの写しでした。一方、分析基盤の設計は問いから導かれます。グレインと切り口は分析の問いの写しであり、NoSQL のキー設計はアクセスパターンの写しでした。そしてどちらの側の設計も、業務を実装から独立に捉えた概念モデルを出発点として共有します。だから通しの設計は、業務と問いの把握から始まり、概念モデルを経て、OLTP と分析基盤へ枝分かれして進みます。原文ではこの流れを段階の表として整理していますが、これは工程表ではなく、依存の向きの整理です。実際の作業は段階を行き来しますが、後の段階の判断が前の段階の成果物に載っている、という向きは変わりません。

もう一つ、押さえておきたい考え方があります。使わない判断も設計のうち、ということです。各章の後半には、決まって採用の判断の節がありました。Data Vault は変化と監査の要件が重いときに、One Big Table は提供先に設計の知識を前提にできないときに、セマンティックレイヤーは同じ指標を使う提供先が複数あるときに見合う、という要領です。通しの設計では、この条件の照合が道具の数だけ繰り返されます。だから出来上がった設計は、使った道具の一覧であると同時に、見送った道具とその理由の一覧にもなります。裏返せば、学んだ道具を総動員した設計は、それだけで見直しの合図です。起きていない問題のために払う対価は、そのまま維持の負債になるからです。

では演習の場面設定です。フィットネスクラブチェーンの運営会社が、24 時間営業のジムを 5 店舗で展開しています。会員は月額プランを契約し、どの店舗も利用できます。入館は、モバイルアプリの会員バーコードをゲートにかざして行います。あなたはこの会社に一人目のデータエンジニアとして加わり、内製する会員管理システムのデータベース設計と、分析基盤の立ち上げを任されました。システムは三つあります。内製の会員管理システムが会員、プラン、契約、店舗を持ち、既製品の入退館ゲートがチェックインのイベントを吐き出し、モバイルアプリが会員証を担います。届いている問いは四つです。店舗別、プラン別の月末会員数の推移。解約率の月次の推移。時間帯別のチェックイン数で見る店舗の混雑。そして、チェックイン当時のプランで区切ったプラン別の利用頻度です。

まず概念モデルです。業務の事実を業務の言葉で確かめます。会員は一つの店舗に所属して入会し、在籍中は常に一つのプランの契約を持ち、プランの変更と退会ができます。チェックインは、会員がどこかの店舗で行います。ここで契約をエンティティとして描くのが、第2章の連関エンティティの判断です。会員とプランの関係は、ある時点では 1 対 1 でも、時間を通せば多対多になります。契約はこの多対多を二つの 1 対多に分解し、さらに期間と料金という、会員にもプランにも属さない、関係そのものの属性を持ちます。

次に論理モデルとキーの選定です。店舗、プラン、会員、契約の四つのテーブルに写します。キーの選定で迷うのは会員番号です。自社で採番する識別子で、一意で NULL にもなりません。それでも主キーには使いません。カードの紛失や不正利用で会員番号を振り直す運用があり得る以上、不変とは言い切れないからです。第2章の ISBN と同じ結論で、主キーはサロゲートキーとし、会員番号は代替キーとして一意性制約で守ります。正規化の点検は、料金の列に現れます。契約テーブルの月額料金は、プランではなく契約に従属します。プランの現行料金は改定されますし、キャンペーンの割引は契約ごとに違うので、契約時点の適用料金は契約の事実として契約の行に置くほかありません。この定価と契約料金の関係は、第3章で見た定価と販売単価の関係の再現です。もう一つの点検は、置かない列の判断です。会員が在籍中か退会済みかを表すステータス列を置きたくなりますが、この値は有効な契約が存在するかどうかから導出できます。導出できる値を列に持てば修正異常の温床になるので、置かず、在籍の判定は契約の側に一元化します。

OLTP の物理モデルでは、これを DDL に落とします。原文の CREATE TABLE 文では、各列に型と NOT NULL を与え、主キー、一意性制約、外部キーに加えて、料金や期間の前後関係の CHECK 制約を宣言しています。契約の期間は、第5章以来の半開区間です。プラン変更は旧契約の終了日と新契約の開始日を同じ日にして接続し、退会は終了日を閉じて後続を作りません。ただし、この DDL には宣言できない業務ルールが一つ残ります。同じ会員の契約期間は重複しない、というルールです。期間の重なりの禁止は、標準的な制約では宣言できません。そこで、アプリケーションの検証で守り、後で DWH 側の検査としても見張る、という配分にします。

ここから分析基盤に進みます。基盤はクラウド DWH への ELT で組みます。ソースごとの取り込み方は、データの残り方で決まります。会員管理システムのテーブルは日次で写します。契約は期間を自分で持つ台帳なので、現在の写しに履歴がそのまま含まれています。ゲートのチェックインは追記のイベントなので、届いた分を積むだけでよい形です。層の構成は、第9章の規約を最初から適用します。staging はソースと 1 対 1 で、結合と集約は置きません。この規約が早速効くのが、ゲートの語彙です。ゲートのイベントは店舗を機器 ID で識別しているので、店舗コードへの読み替えには機器マスタとの結合が要り、これは staging ではなく intermediate に置きます。次は統合層の要否です。ソースは二つ、増えても三つで、ソースをまたぐ主題は会員と店舗だけ、その語彙は会員番号と店舗コードにそろっています。ソースの追加予定はなく、監査の要件もありません。したがって Data Vault はもちろん、第3正規形の統合層も立てず、読み替えは intermediate で足りると判断します。ただし、この判断の前提であるビジネスキーが全社の語彙であることは、文書として残しておきます。買収や新業態でソースが増え、突き合わせのロジックが散らばり始めたら、第7章の時機の判断に戻ります。

マートの設計は、バスマトリクスで計画します。問いの一覧から、チェックイン、月次の会員資格、退会という三つのビジネスプロセスを拾い出し、どれも日付、会員、店舗のディメンションにつながることを確かめます。グレインは三つ宣言します。チェックイン 1 回で 1 行のトランザクションファクト。月末時点の在籍会員 1 人で 1 行の周期スナップショットファクト。そして退会 1 件で 1 行のファクトです。チェックインのファクトには、金額や数量にあたるメジャーが一つもありません。チェックインは起きたこと自体が事実であり、集計はもっぱら行を数えることになります。Kimball はこれを factless fact table と呼びます。

この設計の要になるのが会員ディメンションです。マーケティングの問いはチェックイン当時のプランで区切りたい、というものなので、プランは Type 2 で持ちます。履歴の問いが現に届いている属性だからです。氏名とメールアドレスは、過去の値で区切る問いが考えにくいので Type 1 とします。そして第5章と違うのが、履歴の獲得です。snapshot は、ソースが現在値しか持たない場合に、定期取得と比較で履歴を組み立てる道具でした。この基盤で履歴が要る属性はプランであり、その履歴は契約テーブルが期間として持っています。業務自体が期間を記録しているのだから、snapshot は使わず、契約から直接 Type 2 の行を組みます。契約 1 件が、そのまま版 1 行になります。サロゲートキーの採番、未来側の番兵値、現在フラグは第5章の部品のままで、snapshot の開始日の席に契約の開始日が座っただけです。検査もここで決まります。各会員の有効期間は重複なく並ぶ、という Type 2 の宣言はテストで見張れますし、この検査は、OLTP の DDL で宣言できなかった契約期間の排他を、ロード後に見張る検査でもあります。これが破れたとき疑うべきは変換ではなく、会員管理システム側のデータの誤りです。

チェックインのファクトは、intermediate のチェックインに、当時の会員の版を割り当てて組みます。会員番号が一致し、かつチェックイン日が版の有効期間に入る行を結合してサロゲートキーを引く、第5章のパターンそのままです。時間帯の切り口は時刻から導けるので、列として焼いてファクトに置きます。これで混雑の問いは、平日に絞って店舗と時間帯ごとに行を数える、スタースキーマの定型の一文になります。当時のプラン別の利用頻度は、サロゲートキーで会員ディメンションと結合し、プランごとにチェックイン数と会員数を数えれば答えられます。1 人あたりの利用回数は、分子と分母を別々に数えて問い合わせ側で割る、第4章の要領です。

会員数の推移は、周期スナップショットで答えます。ソースには月末に在籍していたというイベントはないので、このファクトの行は、日付ディメンションの月末日と、会員ディメンションの有効期間を照合して生成します。月末ごとに、その日に有効だった版が 1 会員 1 行で並ぶので、店舗別、プラン別の月末会員数は行数を数えるだけです。ただし半加法の注意がそのまま効きます。会員数は店舗やプランをまたいでは合計できますが、月をまたいだ合計は意味を持ちません。退会のファクトは、契約の終わり方から導出します。契約が閉じ、同じ日に始まる後続の契約がないことが、退会の定義です。後続がある閉じた版はプラン変更なので、退会には数えません。退会とは何かという決定が、このモデルの一箇所だけに書かれたことになります。

提供の形と指標の定義に進みます。店舗のスタッフは SQL を書かず、混雑の表をスプレッドシートで見たいと言っています。提供先に設計の知識を前提にできない、という第8章の条件がそのまま当てはまるので、チェックインのファクトに各ディメンションの属性を写した一枚の OBT を導出して渡します。定義はスタースキーマの側に残り、OBT は写すだけの層にとどめます。一方、解約率には、テーブルの追加では答えません。解約率は、当月の退会数を前月末の会員数で割った比率であり、分子と分母が別のファクトから来ます。この計算式を各部門がそれぞれの SQL に書けば、第9章で見た食い違いが再演されます。そこで指標は宣言に出します。会員数と退会数をそれぞれ指標として宣言し、解約率はその比として宣言する、という構成です。解約率とはこの二つの数の比である、という決定が一箇所に書かれ、BI もスプレッドシートも同じ定義から同じ数字を受け取ります。

開業から半年、アプリにワークアウトを記録する機能が加わりました。記録はドキュメントデータベースに、1 回のワークアウトが 1 文書として入り、文書の中に種目の明細が配列で埋め込まれています。データチームは第10章と同じ二つの立場で関わります。まず集約の境界のレビューです。種目の明細はワークアウトと常に一緒に読み書きされ、記録後は増えも変わりもしないので、埋め込みが正しい形です。会員と店舗は会員番号と店舗コードの参照にとどまっており、全社の語彙と決めたビジネスキーが、新しいソースとの合流点としてここでも効いています。次に取り込みです。staging は 1 文書 1 行のまま型付けだけを行い、配列を行に開く操作は、行数を変える操作なので intermediate に置きます。マートには、ワークアウト中の種目 1 件で 1 行のファクトを足し、種目の一覧はリポジトリの seed として取り込んで専用のディメンションにします。ソースが一つ増えても、増える実装が数枚のモデルに収まり、既存のディメンションには手を入れずに済みます。これが、第6章でバスへの接続として確かめた効果です。

最後に、出来上がった設計を振り返ります。原文では、第1章から第10章までの各章について、この設計に現れた判断を表で対応づけています。そのどれもが、フィットネスクラブという題材の業務と問いから導かれました。プランを Type 2 にしたのは当時のプランで区切る問いが届いていたからであり、統合層を見送ったのはソースが少なく語彙がそろっていたからであり、snapshot を使わなかったのは契約が期間を記録していたからです。題材が変われば、同じ条件の照合が別の結論を出します。契約のような台帳を持たないドメインなら snapshot が要りますし、買収でソースが増え続けるなら統合層が立ちます。変わらないのは結論ではなく、結論を導く条件の側です。

この章のまとめです。本書は、正規化からセマンティックレイヤーまでの技法を、この決定をどこに一度だけ置くか、という問いへの答えとして学んできました。総合演習では、その判断を一つのドメインの上で通しで組み合わせ、使う道具と見送る道具を条件に照らして選びました。残るのは、読者自身のドメインでこの手順を歩くことです。業務を聞き、問いを集め、概念モデルを描き、キーを選び、グレインを宣言し、道具ごとの条件に照らして判断を下す。迷ったときは、対応する章の採用の判断の節に戻ればよいのです。以上で、第11章を終わります。これで全11章の読み上げを終わります。
