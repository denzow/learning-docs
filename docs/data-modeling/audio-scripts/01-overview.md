対象章：[第1章 データモデリングの全体像](../01-overview.md)

第1章、データモデリングの全体像。この章では、データモデリングという活動の全体像をつかみます。手がかりとして、データモデルを整理するための二つの軸を学びます。一つは抽象度の軸で、モデルを概念モデル、論理モデル、物理モデルという三つのレベルに分ける考え方です。もう一つは用途の軸で、データベースに届く処理、つまりワークロードを OLTP と OLAP の二つに分ける考え方です。この二つの軸を頭に入れておくと、以降の章で学ぶさまざまな技法を、地図の上に位置づけるように整理できるようになります。

まず、データモデリングとは何か、というところから始めます。データベースに新しいテーブルを作るとき、開発者は CREATE TABLE 文を書きます。しかしその一文の背後には、実は段階の異なる決定が積み重なっています。業務のどの情報を記録するのか。それをどんな構造で持つのか。そして、どの製品の上でどう実装するのか。この一連の決定を組み立てる活動がデータモデリングであり、その成果物がデータモデルです。テーブル定義を書くこと自体は最後の一歩にすぎない、という点をまず押さえてください。

では、一つ目の軸である抽象度の話に入ります。同じ業務を対象にしても、データモデルは読み手と目的に応じて、抽象度を変えて描きます。慣例として、抽象度の高い順に、概念モデル、論理モデル、物理モデルの三つのレベルに分けます。この三分は、1975年の ANSI/SPARC の三層スキーマアーキテクチャに由来する考え方ですが、実務ではこの三つの呼び名で覚えておけば十分です。

一つ目の概念モデルは、業務上の関心事、つまりエンティティと、それらの関係を、実装から独立に表したモデルです。たとえば、顧客が注文を行う、注文は複数の明細を含む、といった業務の言葉だけで書かれ、データ型やキーは持ちません。読み手には業務側の関係者も含まれるので、図一枚で業務の構造について合意することが目的になります。

二つ目の論理モデルは、概念モデルを特定のデータモデル体系に写したものです。このドキュメント群では、主にリレーショナルモデルを使います。ここでは属性、主キー、外部キー、そして正規化の度合いまでを決めます。リレーショナルモデルという体系には従いますが、特定の DBMS には依存しません。テーブル構造に関する設計判断の大半は、この論理モデルのレベルで下されます。

三つ目の物理モデルは、論理モデルを特定の DBMS 上の実装として表現したモデルです。データ型の選択、インデックス、パーティション分割、ストレージ形式など、性能とコストに関わる決定をここで行います。成果物は、実際に実行できる DDL になります。

なぜわざわざ三つに分けるのでしょうか。それは、変わる速度と変わる理由が、レベルごとに違うからです。顧客が注文を行う、という業務の構造は、データベース製品を乗り換えても変わりません。一方で、物理的な実装は、DBMS の変更やデータ量の増加によって作り直しになります。レベルを分けておけば、たとえば DWH を別の製品へ移行するときも、概念モデルと論理モデルはそのまま持ち越して、物理モデルだけを設計し直せばよいことになります。

次に、二つ目の軸である用途の話です。テーブル構造の善し悪しは、構造単体では決まりません。そのテーブルに、どんな読み書きが届くかで決まります。データベースへのワークロードは、大きく二つに分けられます。

一つは OLTP、オンライントランザクション処理です。これは業務処理そのものを支えるワークロードです。注文の登録や在庫の引き当てのように、少数の行を特定して読み書きする処理が高い頻度で届き、応答は即時でなければなりません。ここで大事なのは、同じ事実を二か所に持つと、片方だけ更新される事故、いわゆる更新異常が起きるという点です。そのため OLTP のモデルは、正規化して冗長を排除する方向に設計します。

もう一つは OLAP、オンライン分析処理です。これは蓄積したデータを分析するワークロードです。月次の売上集計のように、大量の行を読み込んで集約する処理が中心で、書き込みはバッチでまとめて行われることが多くなります。問い合わせのたびに複数のテーブルを結合するコストを避けたいので、OLAP のモデルはあえて冗長を許し、非正規化する方向に設計します。

二つの違いを整理すると、こうなります。主な処理は、OLTP が少数行の読み書き、OLAP が大量行の集計です。主な利用者は、OLTP が業務アプリケーション、OLAP が分析者や BI ツールです。扱うデータの範囲は、OLTP が現在の状態、OLAP が履歴を含む長期間です。設計の方向は、OLTP が正規化、OLAP が非正規化です。代表的な製品を挙げると、OLTP 側が PostgreSQL や MySQL、OLAP 側が BigQuery や Snowflake です。

データエンジニアの仕事は、この二つの世界をつなぐ位置にあります。OLTP システムに蓄積されたデータを抽出し、OLAP に適した構造へ写し替えて、DWH に置くのが仕事です。以降の章で学ぶ技法の多くは、この対比の上に載っています。第3章で学ぶ正規化の理論が OLTP 側の設計を支え、第4章のディメンショナルモデリングや第8章の One Big Table が OLAP 側の設計を支える、という関係です。

ここからは具体例です。書籍のオンラインストアの注文業務を題材に、三つのレベルそれぞれの成果物と、OLTP と OLAP で物理モデルがどう変わるかを、順に見ていきます。

まず概念モデルです。顧客が書籍を注文する、という業務は、顧客、注文、注文明細、書籍という四つのエンティティで表せます。関係は三つです。顧客は注文を行う。注文は少なくとも一つの明細を含む。そして書籍は明細から参照される。原文ではこれを ER 図一枚で示していますが、図には型もキーもありません。一つの注文は一人の顧客に属する、といった業務上の事実だけを表しているので、業務側の関係者とレビューして合意できます。

次に論理モデルです。概念モデルをリレーショナルモデルに写すと、エンティティはテーブルになり、関係は外部キーになります。顧客テーブル customers は、主キーの customer_id と、名前、メールアドレスを持ちます。注文テーブル orders は、主キーの order_id と、外部キーの customer_id、そして注文日時を持ちます。注文明細テーブル order_items は、order_id と行番号の複合主キーを持ち、外部キーとして書籍の ID、さらに数量と単価を持ちます。書籍テーブル books は、主キーの book_id と、タイトル、定価を持ちます。

この論理モデルのレベルで下す設計判断の例が、単価、つまり unit_price の置き場所です。書籍の定価は books テーブルにあるのだから、明細にも単価を持つのは、一見すると冗長に見えます。しかし定価は改定されることがあります。注文時点の販売価格を明細の側に記録しておかなければ、過去の注文金額を再現できなくなってしまいます。これは DBMS の都合ではなく、業務の要請です。だからこそ、物理モデルではなく論理モデルの段階で決めるのです。

続いて、OLTP 側の物理モデルを見ます。論理モデルを DDL に落とす段階です。原文では orders と order_items の CREATE TABLE 文を示しています。内容としては、各列に BIGINT や TIMESTAMP といった具体的なデータ型を与え、NOT NULL 制約を付け、主キーと外部キーを宣言する、というものです。ここで初めて、特定の DBMS で実行できる形になります。

OLTP の典型的な問い合わせは、特定の注文一件の内容確認です。原文の SQL は、注文番号を一つ指定して、orders と order_items と books の三つのテーブルを結合し、その注文の明細ごとに書籍のタイトル、数量、単価を取り出すクエリです。ポイントは、主キーでまず一行に絞ってから結合することです。これなら、テーブルがどれだけ大きくても、応答時間はほぼ一定に保てます。正規化された構造は、この種のアクセスととても相性がよいのです。

最後に、OLAP 側の物理モデルです。同じ業務データでも、分析用の DWH では別の物理モデルを選びます。月次の売上をタイトル別に集計する分析が毎日走るのなら、問い合わせのたびに三つのテーブルを結合するのではなく、結合済みのテーブルをあらかじめ作っておきます。原文では dbt のモデルとして、この結合済みテーブルの作り方を示しています。OLTP 側から取り込んだ注文、明細、書籍のテーブルを結合し、注文日や書籍のタイトル、そして数量かける単価で計算した金額の列まで持たせた、fct_order_items というテーブルを作るクエリです。こうしておけば、分析の問い合わせは、このテーブル一つに対する集計になります。注文日から年と月を取り出し、タイトルごとに金額を合計する、というシンプルなクエリで済みます。

ここで気づいてほしいことがあります。書籍のタイトルを明細ごとに複製して持つのは、OLTP なら更新異常のもとになる冗長です。しかし DWH では事情が違います。このテーブルは直接書き換えるものではなく、元データから定期的に作り直すものです。そのため、複製に起因する矛盾は起きにくくなります。また、列指向ストレージの DWH は、問い合わせに必要な列だけを読みます。列を複製して増やしても、集計のコストはほとんど増えません。つまり、同じ概念モデルから出発しても、ワークロードが違えば、論理モデルから下の正解は変わるのです。この非正規化の設計技法は、第4章と第8章で詳しく扱います。

それでは、この章のまとめです。データモデリングとは、業務の何を記録するか、どんな構造で持つか、どう実装するかという、段階の異なる決定を組み立てる活動でした。モデルは抽象度に応じて、概念モデル、論理モデル、物理モデルの三つに分かれ、変わる速度が違うからこそ分けて管理します。そしてテーブル構造の善し悪しは、届くワークロードで決まります。少数行を即時に読み書きする OLTP では正規化を、大量行を集計する OLAP では非正規化を選ぶのが基本の方向です。データエンジニアは、この二つの世界の間でデータを写し替える役割を担います。以上で、第1章を終わります。
