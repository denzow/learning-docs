# 第7章 Data Vault（読み上げ原稿）

対象章：[第7章 Data Vault](../07-data-vault.md)

第7章、Data Vault。この章では、ソースとマートの間に置く統合層の、もう一つのモデリング法である Data Vault を学びます。前の章で扱った Inmon の方式は、統合層を第3正規形で設計しました。Data Vault はそれとは異なり、ソースから届いた変更をそのまま保存することを設計の中核に据えます。特徴は、Hub、Link、Satellite という三種類のテーブルへの分解です。章の後半では、書籍オンラインストアが実店舗に進出する場面を題材に、統合層を実際に Data Vault で組み立てます。

はじめに、第3正規形で作った統合層の弱点を確認します。第3正規形のモデルは、業務の事実を重複なく一度だけ持つ、安定した土台でした。ただしその安定は、顧客とは何か、注文とは何かを全社で一つに定めるという合意の上に成り立っています。この前提が、変化の速い環境では二つの弱点になります。

第一の弱点は、ソースの追加と変更に弱いことです。新しいソースの事実が、合意済みの形に収まらないことがあります。すると、テーブルの分解や列の意味を設計し直すことになります。統合層はすべてのマートが共有する源ですから、改修の影響はロードとマートの全体に波及します。

第二の弱点は、入り口で解釈を確定させてしまうことです。複数のソースが同じ書籍について食い違う値を届けたとき、統合層に正しい一つの値を格納するには、どちらを正とするかの判断を、ロードの時点で適用するしかありません。すると、判断より前の、ソースが実際に届けた値は統合層に残りません。あとから正とするソースを入れ替えたくなっても、過去にさかのぼって統合をやり直せないのです。レポートの数字の根拠を、ソースに記録されていた値まで遡って示すという監査の要件にも、同じ理由で応えられません。

Data Vault は、この二つの弱点への回答として設計されています。出発点は、統合層の仕事の割り切りです。統合層は、ソースが何を言ったかを漏れなく保存することに徹します。どれが正しいかの判断は、マートを作る段階へ遅らせます。考案者の Linstedt はこれを、真実の単一版ではなく、事実の単一版を持つのだと言い表しています。この割り切りは、変換の分類として明文化されています。入り口で適用してよいのは、型をそろえる、文字コードを整えるといった、値の意味を変えない変換だけです。これをハードルールと呼びます。一方、どのソースの値を採るか、二つの記録を同じものとみなすかといった、意味を選ぶ変換はソフトルールと呼び、統合層の後段で適用します。ソフトルールを適用する前の姿が層として残るので、規則を変えても、保存済みの事実から結果を作り直せます。もう一つの規則は、追記だけで運用することです。届いた事実をあとから書き換えると記録が壊れるので、更新と削除は行わず、新しい事実は常に新しい行として足します。

保存に徹するだけなら、ソースの写しを積み上げるだけでも足りるように見えます。実際、写しに取得時刻を付けて捨てずに積む持ち方もあり、監査の要件だけならそれで満たせます。Data Vault が写しの蓄積と違うのは、保存の形をソースの構造から切り離す点です。写しの蓄積では、ソース側の構造変更がそのまま層の構造変更になり、ソースをまたいだ同じ主題は別々のテーブルに散らばったままです。Data Vault は、どのソースから届いた事実も、三種類の部品に分解して格納します。分解の軸は、変わりにくさです。一つ目は、業務が対象を指すのに使うビジネスキー。ISBN や会員番号のことで、システムが入れ替わっても最後まで残る、最も安定した部分です。二つ目は、どのキーとどのキーが結びついたかという関係。業務の進め方が変わると、結び方も変わります。三つ目は、書名や価格のような記述の属性で、これが最も頻繁に変わります。この三つを、それぞれ Hub、Link、Satellite という別のテーブルに置きます。安定したものと変わりやすいものを同居させなければ、変化は、変わりやすい部品への追記と、新しい部品の追加だけで受け止められるからです。

三種類を順に見ていきます。Hub は、一つの主題のビジネスキーの値の一覧、いわば台帳です。書籍の Hub なら、どのソースに現れたかを問わず、これまでに現れたすべての ISBN が一行ずつ並びます。列はビジネスキーそのものと、そこから計算したハッシュキー、最初に現れた時刻、最初に届けたソースの名前だけで、書名も価格も持ちません。属性はソースごとに食い違い、頻繁に変わるからです。Hub の設計で決めることは、実質的にビジネスキーの選定だけです。システム内部の連番ではなく、業務がソースをまたいで対象を指すのに使っているキーを選びます。主キーには、ビジネスキーからハッシュ関数で計算したハッシュキーを使います。連番と違って採番の状態を持たず、同じキーからはどこで計算しても同じ値が出る、という性質があとで効いてきます。

Link は、二つ以上の Hub にまたがる、キーの組の一覧です。注文1001は会員42のものだ、という結びつきが一行になります。ここでも、数量や金額のような属性は持ちません。Link の特徴は、カーディナリティを常に多対多として持つことです。今の業務では一つの注文に一人の会員でも、その制約をテーブル構造に焼き込むと、業務が変わったときに構造の改修になります。組を行として持つ形なら、新しい結び方は行が増えるだけで受け止められます。これは、事実の形を業務の制約どおりに固定するという正規化の方向とは逆の選択です。統合層は受け入れを優先し、制約の検査は下流のマートに任せるのです。先ほどのハッシュキーの効用は、この Link のロードに現れます。注文番号と会員番号からそれぞれのハッシュキーを計算すれば、Hub を結合して引き当てる必要がありません。ロードが互いの完了を待たないので、テーブルが増えても並列に走ります。

Satellite は、一つの Hub または Link に付く、記述属性の履歴です。主キーは親のハッシュキーとロード時刻の組で、属性が変わるたびに新しい行を追記します。第5章のタイプ2と同じ問題を解いていますが、持ち方が一つ違います。有効期間の終わりを表す列を持たないのです。終端を書き込むには前の行の更新が必要になり、追記だけという規則が破れるからです。終端は、問い合わせの時点で次の行の開始時刻から導きます。変更の検出にはハッシュディフという仕組みを使います。比較対象の属性列をまとめてハッシュした値を各行に持たせ、ソースの現在値から計算したハッシュが最新行と違ったら、新しい行を足します。また、Satellite は一つの親に複数付けられます。注文システムの言う書名と POS の言う書名を別々のテーブルに積んで、どちらの言い分も混ぜずに残す、ソース別の分割。頻繁に変わる属性とめったに変わらない属性を分ける、変更頻度別の分割。この二つの軸があります。

層構成の中での位置づけも確認しておきます。ソースの事実を分解してそのまま積む層をロウボルトと呼びます。ソフトルールの適用結果を作り置く場合は、ビジネスボルトとして隣に並べます。利用者に見せる層は、これまでどおりスタースキーマの情報マートで、Vault から導出して作ります。利用者に Vault を直接見せないのは、結合が多いことと、どのソースの値を採るかがまだ解決されていないためです。つまり Data Vault は、Kimball のスタースキーマと競合しません。Inmon の統合層の席に座る、もう一つのモデリング法です。

採用の判断にも触れます。Data Vault の代償は、まず物量です。テーブル数は第3正規形のモデルの数倍になり、読み出すときの結合数も増えます。この物量を手書きで維持するのは現実的でないため、ロードのパターンを規約で固定し、コード生成で量産することが実務の前提になります。この代償が見合うのは、ソースの数が多くこれからも増え続けるとき、数字をソースの記録まで遡って説明する監査の要件があるとき、複数のチームが統合層を並行して拡張するときです。裏返せば、ソースが少なく安定していて監査の要件も薄いなら、分解の物量だけを払うことになります。判断は二段に分かれます。まず統合層を立てるか、これは前の章の問いです。立てるなら第3正規形と Data Vault のどちらでモデリングするか、これが本章の問いです。

ここからは具体例です。実店舗の一号店を出すことが決まりました。レジは POS システムで、書籍はバーコード、すなわち ISBN でスキャンされます。会員は、店舗でも同じ会員番号をアプリのバーコードで提示します。さらに翌年には、電子書籍ストアの開設も計画されています。ソースは三つになり、四つ目も見えています。POS の商品マスタが届き始めると、同じ書籍の書名や価格がソースごとに食い違うことも分かってきました。突き合わせのロジックがステージングに散らばって膨らみ始める、前の章の最後に置いた時機です。そこで統合層を立てます。第3正規形ではなく Data Vault を選ぶ根拠は、ソースの追加が続くと確定していることです。まだ仕様の見えない電子書籍ストアまで収まる全社モデルを先に合意するより、届いた事実から積み上げて拡張で受け止める方が、この状況に合っています。

最初の仕事は、主題ごとのビジネスキーの特定です。書籍は ISBN、会員は会員番号、注文はオンラインの注文番号です。店舗販売は POS のレシート番号ですが、レシート番号は店舗の中でしか一意でないため、店舗コードとの複合キーにします。この例が示すとおり、ビジネスキーの特定は自明な作業ではありません。選んだキーの上にすべての Link と Satellite が載るので、設計作業の中心は、図を描くことではなくこのキーの合意にあります。キーが決まれば、骨格は分解の規則から機械的に決まります。この例では Hub が四つ、Link が四つ、Satellite が六つの、合計十四テーブルになります。書籍の Hub には注文システムと POS の両方から ISBN が集まり、その記述はソース別の二つの Satellite に積まれます。非会員の店舗販売は、販売と会員を結ぶ Link に行ができないだけで、構造の変更なしに受け止められます。

ロードは dbt で書きます。Vault は追記だけで運用するので、実行のたびに作り直すのではなく、前回の結果に行を足すインクリメンタル方式を指定します。Hub のロードは、各ソースのステージングから ISBN を集め、まだ台帳にないものだけを追記するクエリです。同じ実行で複数のソースに現れた ISBN は一行に絞ります。このロードの規則はどの Hub でも一字一句同じで、規則が固定されているからこそコード生成で量産できます。Link のロードでは、注文番号と明細番号からハッシュキーを計算し、まだ台帳にない組だけを追記します。書籍のハッシュキーは Hub を結合して引き当てるのではなく、ISBN から直接計算します。だからこのロードは、Hub のロードの完了を待ちません。Satellite のロードは、ソースの現在値から計算したハッシュディフを最新行と比べ、違う行だけを追記するクエリです。第5章で dbt のスナップショットが担っていた変更検出と履歴の獲得は、この層に移ります。

情報マートの形は、第4章から何も変わりません。変わるのは材料で、ステージングからではなく Vault から導出します。書籍のディメンションを再構築すると、遅らせてきたソフトルールがここで初めて現れます。二つの Satellite からそれぞれ最新の行を取り、書名はオンラインストアの表記を正とし、オンラインで扱いのない店頭専売の書籍だけ POS の表記を使う、という判断を、値の優先順位を選ぶ一つの式として書きます。この判断はマートのこのモデルだけに書かれています。Vault には両方の言い分が残っているので、店舗の表記を正に改めることになっても、このモデルを書き換えて再実行するだけで済みます。履歴つきの顧客ディメンションも Satellite から導けます。終端の列を持たない Satellite から、次の行の開始時刻を取って有効期間を導出すれば、第5章と同じ形になります。期間の重複と欠落は導出の式が保証するので、第5章でテストに見張らせた検査は、構造上不要になります。検査の対象は、台帳の一意性や Satellite から Hub への参照といった、保存の規則そのものに移ります。

最後に、この統合層は見合うのかを振り返ります。この Vault は、ステージングとマートの間に新しく挟まった十四枚のテーブルです。前の章までこの場所には何もなかったのですから、物量の代償は明白です。増えた分が買っているのは、次の拡張の安さです。電子書籍ストアが開設されたら、足すものは、ステージングのモデルと、電子書籍ストアの言い分を積む Satellite、購入イベントの Hub と Link とその Satellite だけです。既存のテーブルとそのロードには一切手を入れません。電子版には紙と別の ISBN が振られるので、書籍の Hub には紙と電子が別の行として並びます。それを同じ作品としてまとめて見るかどうかはソフトルールで、事実は Vault に、解釈はマートに置くという分担が、この拡張でも保たれます。ソースが二つで止まっていた前の章の時点でこれを立てていたら、分解の物量だけを払っていたでしょう。ソースの追加が続くと確定した状況で、初めて代償が回収に転じます。Data Vault は常に正しい設計ではなく、変化の速さに賭ける設計なのです。

この章のまとめです。Data Vault は、統合層のモデリング法の一つで、ソースが何を言ったかの保存に徹し、どれが正しいかの判断をマートへ遅らせます。事実は、安定したビジネスキーの台帳である Hub、キーの組の台帳である Link、記述の履歴である Satellite に分解して、追記だけで積み上げます。この分解によって、ソースの追加は既存のテーブルに手を入れずに受け止められ、ソースに記録されていた値まで遡る監査にも応えられます。代償はテーブルと結合の物量で、ロードの自動化が実務の前提です。だから採否は、変化と監査の要件の重さで判断します。次の章では、利用者に見せる層に働く逆向きの力、結合をあらかじめ済ませた一枚の広いテーブル、One Big Table を扱います。以上で、第7章を終わります。
