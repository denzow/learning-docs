# 第4章 ディメンショナルモデリング（読み上げ原稿）

対象章：[第4章 ディメンショナルモデリング](../04-dimensional-modeling.md)

第4章、ディメンショナルモデリング。前の章では、非正規化を管理できる条件を判断基準として整理しました。しかしあの基準が答えるのは、崩してよいかどうかであって、どんな形に崩すか、ではありません。分析用のデータウェアハウスのテーブル群を、どんな形に組めばよいのか。その指針として、この章では三十年来の定石を学びます。Ralph Kimball が1990年代に体系化した、ディメンショナルモデリングです。分析の問いの形からファクトとディメンションという二つの役割を導き、その配置であるスタースキーマと、設計を進める手順である Kimball の設計プロセスを扱います。具体例では、書籍オンラインストアの注文データを、スタースキーマとして設計し直します。

出発点は、分析者が立てる問いの形です。先月の売上はいくらだったか。書籍別ではどうか。休日と平日で差はあるか。よく見ると、形はどれも同じです。測る数値が一つあり、それを区切る切り口が付いています。売上金額という数値を、月ごと、書籍ごと、休日か平日か、という切り口で区切っている。SQL に写せば、測る数値は SUM などの集約関数の中に、切り口は GROUP BY と WHERE に現れます。

ディメンショナルモデリングは、この問いの形をそのままテーブルの形にする技法です。測る数値をメジャー、切り口をディメンションと呼び、メジャーを集めるテーブルと、切り口ごとの属性を集めるテーブルに分けて設計します。第2章の ER モデリングは業務の対象ごとに、第3章の正規化は事実の単位ごとにテーブルを分けました。ここでの分割の単位は、分析の問いにおける役割です。同じリレーショナルなテーブルを作るのでも、何に沿って分けるかが違うわけです。

まず、測る側を受け持つのがファクトテーブルです。業務で起きた測定可能な出来事を一行ずつ記録します。列はメジャーと、各ディメンションを指す外部キーでほぼ占められます。説明のための文字列を持たないので、行数は多いが列は細い、という形になります。

ファクトテーブルの設計は、グレインを決めることから始まります。グレインとは、一行が現実の何に対応するかの宣言です。注文明細一行、とか、書籍と日付の組ごとの在庫残高一行、というように、業務の言葉の一文で宣言します。なぜ宣言を先に固定するのか。粒度の違う行が混ざったテーブルでは、集計が信用できなくなるからです。たとえば明細の行と注文合計の行が同じテーブルに同居すると、SUM は同じ売上を二重に数えてしまいます。

メジャーには、どの切り口に沿って合計してよいかの違いがあり、加法性と呼んで三つに分けます。一つ目は加法的なメジャーで、どの切り口で区切って合計しても意味を持ちます。販売金額や数量がそうです。二つ目は半加法的なメジャーで、一部の切り口でしか合計できません。在庫残高が典型で、書籍をまたいで合計はできますが、月曜の在庫と火曜の在庫を足す、という日付をまたいだ合計は意味を持ちません。三つ目は非加法的なメジャーで、単価や比率のように、合計そのものが意味を持たないものです。集計の主役は加法的なメジャーです。比率のような値はそのまま持たず、分子と分母を加法的なメジャーとして持ち、問い合わせの側で割って求めます。平均単価が欲しいなら、単価の平均ではなく、金額の合計を数量の合計で割るのです。

またファクトテーブルには三つの種類があります。出来事の発生ごとに一行を追加するのがトランザクションファクト。日次や月次の周期で、その時点の状態を写すのが周期スナップショットファクトで、日次の在庫残高が典型です。半加法的なメジャーの主な置き場になります。そして、注文から出荷、配送完了までのような一連の業務プロセス一件を一行とし、節目の日付を進行に応じて埋めていくのが累積スナップショットファクトです。工程間の所要日数の分析に向きます。

もう一方の、切り口の側を受け持つのがディメンションテーブルです。誰が、何を、いつ、という言葉でファクトの行を説明する属性を集め、絞り込みとグループ化の語彙を提供します。分析者が GROUP BY や WHERE に書けるのはディメンションにある列だけですから、属性の列が多いほど、答えられる問いが増えます。そして構造は、あえて正規化しません。書籍のディメンションに著者名の連結を持つのも、意図した設計です。ディメンションテーブルは変換処理だけが書き込み、実行のたびに作り直され、読み取り専用で使われる。つまり第3章で整理した、非正規化を許してよい三つの条件を満たしているのです。

最も定番のディメンションは日付です。年や月や曜日は日付関数でも計算できるので、テーブルにするまでもないように見えます。しかし日付ディメンションの価値は、計算では導けない属性を持てることにあります。祝日かどうか、営業日かどうか、セール期間か。これらはカレンダーという業務知識であり、テーブルとして持つほかありません。日付を主キーにすれば、十年分でも四千行に満たない小さなテーブルで済みます。

ここでファクトとディメンションの行数の非対称に注目してください。明細のファクトが数千万から数億行に育つ一方で、顧客は数十万、書籍は数万、日付は数千の桁にとどまります。ディメンション側の非正規化が容量の点でほとんど問題にならないのは、この非対称のためです。

ファクトテーブルを中心に置き、ディメンションテーブルが外部キーで結ばれて取り囲む配置を、スタースキーマと呼びます。ER 図に描いたときの星形にちなむ名前です。この配置の利点は、問い合わせが定型になることです。どの問いも、ディメンションの属性で絞り込み、ディメンションの属性でグループ化し、ファクトのメジャーを集約する、という一つの形の SQL に収まります。結合は常にファクトとディメンションの一段だけです。定型であるおかげで、BI ツールはスタースキーマを前提に問い合わせを自動で組み立てられ、分析者は問いに集中できます。なお、ディメンションをさらに正規化して枝分かれさせた配置はスノーフレークスキーマと呼ばれますが、Kimball はこれを推奨しません。ディメンションはもともと小さいので容量の節約はわずかで、その割に結合の段数と、分析者が把握すべきテーブルの数が増えるからです。

キーについても触れておきます。Kimball の設計では、ディメンションテーブルの主キーに、ソースシステムの ID ではなく、DWH 側で新たに振るサロゲートキーを使います。理由は履歴です。顧客の属性が変わったとき、変更前と変更後を別々の行として残すなら、同じ顧客 ID を持つ行が二つできて、その ID では行を特定できなくなります。行を特定するキーは、DWH の側で振り直すほかないのです。ただし、この必要が生じるのは履歴を持たせるときです。常に現在値で上書きするディメンションなら、ソースの ID をキーに使っても差し支えありません。履歴の持ち方は第5章の Slowly Changing Dimensions で扱うので、この章の具体例は上書き方式にとどめます。

部品がそろったところで、設計をどの順で進めるかです。Kimball は四つのステップを定式化しました。第一に、ビジネスプロセスの選択。注文や出荷といった、測定の対象とする業務活動を選びます。第二に、グレインの宣言。ファクトテーブルの一行が何かを、業務の言葉で宣言します。Kimball は、それ以上分けられない最も細かい粒度、つまり原子的グレインを推奨します。集計して粗くした粒度は、あとから出てくる想定外の切り口の問いに答えられないからです。第三に、ディメンションの識別。グレインの一行について値が一意に決まる記述を列挙します。第四に、ファクトの識別。グレインと整合するメジャーを列挙し、整合しない数値は別のファクトテーブルに割り当てます。この手順の要点は、グレインの宣言が識別より前にあることです。一行が何かが決まってはじめて、一意に決まるか、整合するか、という判定が下せるのです。ビジネスプロセスを一つずつ選んでスキーマを作っていくと、注文のスキーマと在庫のスキーマが同じ日付や書籍のディメンションを共有する形が自然に生まれます。複数のファクトから共有されるディメンションを適合ディメンションと呼び、スキーマ群を一つの DWH へつなぎ合わせる役割を担います。

では具体例です。第1章では、月次のタイトル別集計のために、書名を明細に複製した結合済みのテーブルを dbt で作りました。その後、休日と平日で売れ行きは違うか、共著の書籍は単著より売れるか、と要望が増えたとします。ここで Kimball の手順を適用します。ビジネスプロセスには注文を選びます。届いている問いはどれも売上についてのものだからです。グレインは、注文明細一行と宣言します。注文一件を一行とする粗い粒度でも売上合計には答えられますが、書籍別の問いには答えられません。ディメンションは、明細一行について一意に決まる記述として、日付、顧客、書籍の三つを挙げます。グレインを先に宣言した効果は、著者の扱いに現れます。共著の書籍では明細一行に複数の著者が対応するので、著者は一意に決まらず、そのままではディメンションになりません。そこで著者の情報は、書籍ディメンションの属性へ畳み込みます。ファクトは数量と単価、それに数量掛ける単価で導出する金額の三つです。金額と数量は加法的で、集計の主役になります。単価は非加法的ですが、注文時点の販売価格という明細の事実なので、明細のグレインと整合し、ここに置いてかまいません。残った注文 ID と明細番号は、メジャーでもなければ、テーブルを立てるほどの属性も持たない、ただの識別子です。この種の列は縮退ディメンションと呼び、ファクトテーブルに直接置きます。

日付ディメンションは、ソースから取り込むのではなく DWH 側で生成します。dbt では、連続した日付の列を生成するマクロで骨格を作り、年や曜日のような計算で導ける属性は式で付け、計算で導けない祝日は、リポジトリで管理する祝日一覧のファイルを結合して写します。セール期間などが必要になったら、同じ要領で列を足せばよいのです。

書籍ディメンションは、正規化された書籍、著者、対応表の三つのテーブルを一枚に畳みます。著者は一冊について複数いるので、表示順にカンマで連結した著者名の文字列と、著者の人数という二つの属性に要約します。このカンマ区切りは、第3章で第1正規形違反の典型として分解した、まさにあの形です。ここでは、変換処理だけが書き、作り直され、読み取り専用という条件を満たしたうえで、意図した設計として再導入しています。共著か単著かで区切る問いには著者数の列が答えます。ただし、特定の著者一人の売上を集計する問いには、連結文字列からでは答えられません。それが実際に必要になったときの道具として、Kimball はブリッジテーブルという技法を示しています。

ファクトテーブルは、第1章の版から説明的な属性を取り除いた形になります。明細と注文を結合して、注文 ID、明細番号、注文日、顧客 ID、書籍 ID、数量、単価、金額だけを選ぶクエリです。第1章の版にあった書名の列は消えています。書籍を説明する属性はすべて書籍ディメンションにあり、ファクト側は ID で指すだけでよいからです。問いが増えて書籍の属性を足したくなっても、変わるのは数万行のディメンションだけで、数億行に育つファクトには手を入れなくて済みます。切り口の追加がディメンション側の変更で閉じることが、一枚のテーブルに列を足し続ける道との違いです。

このスキーマで、休日と平日で書籍ごとの売れ行きは違うか、という問いは一つの SQL になります。ファクトを日付ディメンションと書籍ディメンションに結合し、週末または祝日かどうかで休日と平日に分け、書名とともにグループ化して、金額を合計するクエリです。祝日の判定は注文データからは導けませんが、このクエリには祝日の一覧も日付の計算も現れません。切り口は日付ディメンションの列として、あらかじめ用意してあるからです。共著と単著の比較に変えるなら、書名を著者数の条件式に差し替えるだけです。どの問いも、ディメンションで区切り、メジャーを集約するという同じ形に収まります。

検査についても、スタースキーマでは何を検査すべきかが設計の宣言から決まります。注文明細一行というグレインの宣言は、注文 ID と明細番号の組が一意である、という検査に翻訳できます。明細が重複すると、すべての集計が静かに水増しされるからです。星形の結合は、ファクトの外部キーが対応するディメンションの行に必ず当たる、という検査に翻訳できます。当たらない行があると、結合でその行が落ち、集計が静かに欠けます。dbt では、この二種類をテストとして宣言しておけます。

最後に、この設計に残る宿題です。顧客ディメンションはソースの写しなので、顧客が属性を変えると、次の作り直しで全行が現在の値になります。過去の注文を集計しても、添えられる顧客の属性はすべて今の値です。当時の会員ランク別の売上のように、注文の時点の属性で過去を区切りたい問いには、上書きでは答えられません。変更を履歴として残す技法が Slowly Changing Dimensions であり、先ほど予告したサロゲートキーが必要になるのもそこです。第5章で扱います。

まとめます。ディメンショナルモデリングは、測る数値と区切る切り口という分析の問いの形を、そのままファクトテーブルとディメンションテーブルに写す技法でした。設計はグレインの宣言から始まり、ビジネスプロセスの選択、グレインの宣言、ディメンションの識別、ファクトの識別という Kimball の四ステップで進めます。ファクトを中心にディメンションが取り囲むスタースキーマは、問い合わせを定型にし、切り口の追加をディメンション側の変更で閉じさせます。ディメンションの非正規化は、行数の非対称と、読み取り専用という使われ方に支えられた、意図した崩し方です。以上で、第4章を終わります。
