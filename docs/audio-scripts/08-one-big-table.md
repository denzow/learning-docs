対象章：[第8章 ワイドテーブルと One Big Table](../08-one-big-table.md)（[演習問題](../exercises/08-one-big-table.md)）

第8章、ワイドテーブルと One Big Table。この章では、結合をあらかじめ済ませた、一枚の広いテーブルという設計を扱います。第7章の統合層は、届いた事実を細かい部品に分解して積み上げる、分解の徹底でした。一方、利用者に見せる層には逆向きの力が働いています。クラウドデータウェアハウスの列指向ストレージと安価な計算資源が、一枚に畳み込むという選択を現実的にしました。この前提の変化を確かめたうえで、ワイドテーブルと One Big Table の設計と代償を考えます。具体例では、スタースキーマから提供用の一枚を導き出し、第4章で持ち越していた著者単位の集計に答えます。

まず、スタースキーマが残した負担の話から始めます。第4章のスタースキーマは、どんな問いも、ディメンションで絞り込み、ディメンションでグループ化し、メジャーを集約する、という一つの形に収めました。ただしその形は、毎回の結合の上に成り立っています。たとえば休日と平日の売れ行きを比べる問いは、ファクトに日付と書籍の二つのディメンションを結合していました。

この結合は、まず計算の負担です。毎朝開かれるダッシュボードは、同じ結合を毎日何百回も実行します。しかも分散環境での結合は、結合キーごとに行を計算ノード間で並べ直す、シャッフルと呼ばれる操作を伴い、ファクトが億の桁に育つほど、これが問い合わせ時間と計算費の主な原因になっていきます。

結合は、使い手の負担でもあります。スタースキーマを正しく問い合わせるには、テーブルの形からは読み取れない、規約の知識が必要です。履歴を持つディメンションへはサロゲートキーで結合すること。グレインの違うファクト同士を直接結合しないこと。これらの規約は、破っても構文エラーにならず、静かに水増しされた数字が返ってくるだけです。提供先が分析チームの中に閉じているうちは教育で守れますが、全社に広がるほど、全員にこの知識を求めるわけにはいかなくなります。

さらに、道具の制約もあります。スプレッドシート、ノートブックのデータフレーム、機械学習の学習データ。どれも一枚の表を入力の前提にしていて、スタースキーマのままでは渡せません。結合を減らしたい要求自体は古くからあり、かつては集計済みテーブルや OLAP キューブ、つまりグレインを粗くして行数を抑える形で応えてきました。明細のグレインのまま、すべての属性を複製する形が採られなかったのは、それが割に合わなかったからです。この損得を変えたのが、クラウドデータウェアハウスのストレージの形式です。

OLTP の製品の多くは行指向、つまり一行分の値をひとまとまりにして格納します。一行の読み書きが一箇所へのアクセスで済むので、行を出し入れする OLTP の操作に向いています。分析の問い合わせは逆で、少数の列を全行にわたって走査します。クラウドデータウェアハウスが採る列指向は、同じ列の値を列ごとにまとめて格納する形式で、この走査に向いています。

列指向の帰結は二つあります。一つ目は、参照しない列は読まれないことです。列が二百あるテーブルでも、問い合わせが触るのが五列なら、走査されるのは五列分だけです。テーブルを広くすること自体は、読み取りをほとんど遅くしません。二つ目は、複製が圧縮で消えることです。同じ列の値がまとめて置かれるので、値の種類が少ない列には辞書圧縮やランレングス圧縮がよく効きます。書名を数億行の明細に複製しても、書名の列は、数万種類の値の辞書と、それを指す参照の並びに縮みます。行指向で同じ複製をすれば、全行がそのまま太ります。

一方で、結合は相対的に高い操作として残りました。シャッフルの費用は圧縮では消えず、行数に応じて掛かり続けます。そうなると、一度の変換で複製を作っておく費用と、問いのたびに結合を払い続ける費用の比較が、後者に不利に傾いていきます。要するに、複製は高く、結合で導く方が安いという行指向の損得が、列指向では反転したのです。複製には更新の異常という書き込み側の危険もありますが、こちらは、変換処理だけが書き込み、実行のたびに作り直され、読み取り専用で使われるという第3章の判断基準が、すでに抑えていました。

この条件の下で自然に現れるのが、結合をあらかじめ済ませておく設計です。結合済みで列の多いテーブルを総称して、ワイドテーブルと呼びます。その徹底形が One Big Table、略して OBT です。一つのビジネスプロセスのファクトについて、グレインを保ったまま、参照するすべてのディメンションの属性を畳み込んだ一枚を指します。利用者はこの一枚を絞り込んでグループ化するだけで、そのプロセスの問いのほとんどに、結合なしで答えられます。置き場所は層構成の最後尾、スタースキーマから流れてきた先です。OBT はスタースキーマから導出する一枚であって、スタースキーマを置き換えるモデリング法ではありません。なぜ導出にとどめるのかは、代償を数えたあとでお話しします。

OBT を実際に組もうとすると、平らな結合では畳み込めない関係が残ります。一対多です。共著の書籍では、明細一行に複数の著者が対応します。著者のテーブルを平らに結合すると、明細の行が著者の数だけ複製され、注文明細一行というグレインの宣言が壊れます。第6章で見た水増しと同じ事故です。第4章では、この関係を著者名の連結文字列と人数に要約して畳み込み、著者単位の集計は諦めていました。連結された文字列からは、著者を取り出せないからです。クラウドデータウェアハウスでは、列の型に配列と構造体、ARRAY と STRUCT が使えるので、明細一行の中に、著者の構造体の配列を一列として格納できます。行数は明細のまま変わらず、多側の情報も失われません。ネストした列も列指向のまま分解して格納されるので、配列の列に触れない問い合わせは、その列を読みもしません。読み出すときは、UNNEST という操作で配列を行に開いてから集計します。このときも行は著者の数だけ複製されますが、結合の副作用として気づかず起きるのではなく、集計の直前に意図して行う展開です。

次に、採用の判断です。OBT の代償は三つ数えられます。第一に、切り口の追加と定義の変更が、一枚全体の再構築になります。スタースキーマでは、切り口の追加はディメンション側の変更で閉じ、数億行のファクトには手を入れずに済みました。OBT では属性が全行に焼き込まれているので、列を一つ足すにも、定義を一つ直すにも、一枚を作り直します。列指向が安くしたのは読み取りであって、数億行の書き直しには相応の計算費が掛かります。

第二に、答えられる問いが一つのプロセスに閉じます。OBT はグレイン一つにつき一枚で、注文の OBT と出荷の OBT を直接結合すれば、第6章と同じ水増しが起きます。プロセスをまたぐ問いには、OBT の世界でもドリルアクロスが必要です。名前に反して、One Big Table は全社を一枚にするテーブルではありません。

第三の代償は、構成を誤ったときにだけ現れますが、最も高くつきます。OBT をソースから直接組み、指標の定義や突き合わせのロジックをその変換に書き始めると、OBT が増えるたびに定義が複製されます。ダッシュボードごとの一枚が別々の定義を持ち始めた姿は、第6章で見た独立データマートのサイロが、提供層で繰り返されたものです。これが、OBT を導出にとどめる理由です。グレインの宣言、適合ディメンション、履歴の表現はスタースキーマの側に一度だけ置き、OBT はそれを平らに写すだけの層にします。ワイドテーブルは提供の形であって、定義の置き場ではないのです。

この代償を払っても見合うのは、次のような場面です。まず、提供先に設計の知識を前提にできない場面。スプレッドシートやノートブックの利用者への提供や、社外への共有です。次に、同じ結合を高頻度で繰り返す場面。定型のダッシュボードなら、事前の一度の結合が毎回の結合を消します。そして、一枚の表を要求する道具に渡す場面。機械学習の特徴量や、データのエクスポートです。裏返せば、結合を自分で書ける分析者が探索的に使う分には、スタースキーマのままの方が融通が利きます。OBT は畳み込んだ時点の切り口に問いを固定しますが、スタースキーマはどのディメンションのどの属性でも、後から自由に組み合わせられるからです。だから両者は置き換えではなく併存になり、BI ツールにはスタースキーマを、一枚を要する提供先には OBT を見せる、という使い分けになります。

では、スタースキーマを飛ばして、最初から OBT だけで始めてよいでしょうか。ソースが一つで、問いが安定していて、履歴の要件もない規模なら、staging から直接一枚を組んでも回ります。実際、第1章はそうやって始めました。しかし切り口の変更が届き、履歴が必要になり、プロセスが増えた時点で、定義を一箇所に置く層が要ることは、第4章から第7章まで一歩ずつ確かめてきたとおりです。

ここからは具体例です。マーケティングチームが自分たちで数字を見たいと言い出し、分析チームの外で SQL が書かれ始めたとしましょう。ほどなく、会議に出た会員ランク別の売上レポートの合計が、ダッシュボードの総売上と合わない、という相談が届きます。原因は結合でした。担当者は注文明細のファクトと顧客ディメンションを、顧客 ID で結合していたのです。顧客ディメンションはランクの履歴を行として持つので、履歴のある顧客では、注文明細が履歴の行数だけ複製されていました。第5章の設計では、ファクトへの結合はサロゲートキーで行い、顧客 ID は突き合わせの手がかりにとどめます。しかしこの規約もまた、テーブルの形からは読み取れない設計者の知識です。そこで、教育で防ぎ続ける代わりに、正しい結合を済ませた一枚を提供することにします。注文明細の OBT、obt_order_items です。

この OBT を作る SQL は、こういう変換です。材料は marts のスタースキーマで、注文明細のファクトに、日付、顧客、書籍の三つのディメンションを、それぞれ正しいキーで結合します。日付ディメンションからは年や月、週末かどうか、休日かどうかといった切り口を写し、顧客ディメンションからは会員ランクを、書籍ディメンションからは書名や定価を写します。著者は、先ほどのネスト構造で畳み込みます。書籍と著者の対応表から、著者名と表示順の組を書籍ごとに配列へ集約し、それを結合するのです。平らな結合と違って行は増えず、グレインは注文明細一行のままです。

事故を起こした結合の規約は、このモデルの中に一度だけ書かれました。サロゲートキーで引くので、写る会員ランクは注文時点の値になり、利用者は有効期間の照合を知らなくて済みます。氏名のような上書きされる属性も同じ要領で写せますが、挙動はスタースキーマと同じで、OBT が変えるのは提供の形だけです。また、列名には order_year のように、どのディメンション由来かが分かる接頭辞を付けます。複数の日付ディメンションを畳み込んだとき、同じ列名が衝突するのを防ぐためです。

この一枚ができると、問い合わせから結合が消えます。第4章の休日と平日の問いは、OBT を週末か休日かで場合分けし、書名でグループ化して、金額を合計するだけの形になります。返る答えは第4章と同じで、違いは結合が消えたことだけです。この形なら、スプレッドシートに写しても、SQL に不慣れな利用者が書いても、結合の誤りようがありません。見た目は第1章で作った結合済みのテーブルに戻りましたが、出自が違います。第1章の一枚は staging から直接組まれ、グレインも定義も自分で抱えていました。今回の一枚は、グレインの宣言も履歴の表現も、すべて上流のスタースキーマが決めたものを写しています。第4章から第7章までの回り道が、一枚の中身の信頼を支えているわけです。

第4章で見送った問いも、ここで回収できます。著者別の売上ランキングを出したい、という問いです。OBT の著者の配列を UNNEST で行に開き、著者名でグループ化して金額を合計します。共著の明細は著者の数だけ展開されてから集計されるので、連結文字列では答えられなかった問いに、ブリッジテーブルを新設せずに答えられました。ただし、この集計では共著書の売上が各著者に全額計上されます。按分が要るなら、金額を配列の要素数で割ればよいだけです。

この層の宣言も、検査に翻訳しておきます。OBT の宣言は、注文明細のファクトの導出であり、グレインを変えない、というものです。であれば、ファクトと OBT とで行数と金額の合計を数えて突き合わせ、食い違ったら失敗するテストを書けば十分です。誤った結合が行を複製すれば数字が増え、内部結合の取りこぼしが行を落とせば減るので、水増しと欠けの両方を一つの検査で捕まえられます。

出来上がった構成では、marts に役割の違う二種類のモデルが並びます。定義を持つスタースキーマと、それを平らに写した提供用の一枚です。セール期間で売上を区切りたい、という次の要望が来たときの流れに、この分担が現れます。どの日がセール期間かを知っているのは日付ディメンションだけで、そこに列を足せば定義の変更は一箇所で済み、OBT はその列を写して再構築するだけです。ダッシュボードが増え、提供する一枚が増えていくと、今度は、どの指標の定義をどの層のどのモデルに置くか、変換の流れ全体をどんな規約で保つか、という問いが現れます。第9章では、この問いへの現在の答えとして、dbt のレイヤリングと、指標の定義を宣言として一元管理するセマンティックレイヤーを扱います。

まとめます。行指向の OLTP では複製が高く、結合で導く方が安かったのに対し、列指向のクラウドデータウェアハウスでは、読まない列は走査されず、複製は圧縮で縮み、結合だけが高い操作として残りました。この反転が、結合を済ませたワイドテーブル、その徹底形の One Big Table を現実的にしました。一方で OBT には、変更のたびの再構築、一つのプロセスに閉じること、そして定義を書き込むとサイロが再演されることという代償があります。だから定義はスタースキーマに一度だけ置き、OBT はそれを平らに写す導出の層にとどめる、というのがこの章の結論です。以上で、第8章を終わります。
