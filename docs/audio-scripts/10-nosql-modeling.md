# 第10章 NoSQL のデータモデリング（読み上げ原稿）

第10章、NoSQL のデータモデリング。この章では、リレーショナルモデルと SQL を前提としないデータベース群、いわゆる NoSQL のデータモデリングを扱います。キーバリュー、ドキュメント、ワイドカラムという三つの型の設計原則を確かめると、どの型にも、問いの形に合わせてデータをあらかじめ畳んでおく発想が設計の出発点になる、という同じ転換が現れます。後半では、電子書籍ストアを題材に、データストアの設計から分析基盤への取り込みまでを行います。

NoSQL は単一の製品や理論の名前ではなく、こうしたデータベース群を緩く束ねた通称ですが、主要な製品は同じ事情から生まれています。2000年代後半のウェブサービスでは、書き込みの量が単一サーバのデータベースの限界を超え、データを複数のサーバに分割するほかなくなりました。分割した途端、結合はサーバをまたぐ突き合わせになって通信が発生し、トランザクションはサーバをまたぐ合意になって待ちが発生します。NoSQL の主要な製品は、この二つを最初から提供しないことと引き換えに、分割と複製を素直に行える構造を選びました。

第1章の区別でいえば、NoSQL が受け持つのは OLTP です。低遅延で読み書きされるアプリケーションのデータストアが主戦場で、自由な切り口の集計という OLAP の問いにはむしろ弱いのです。だからデータエンジニアにとって NoSQL は、自分が設計するテーブルではなく、取り込むべき新しい種類のソースとして現れます。それでも設計原則を知る必要があるのは、集約の境界や履歴の残り方といったソース側の設計が、取り込みの設計をそのまま左右するからです。なお三つの型は、関連するデータのかたまりを単位に読み書きする点が共通しており、まとめて集約指向と呼ばれます。

次に、設計原則の転換です。リレーショナルの設計は構造を先に決めます。業務の事実を正規化して一度だけ置き、どの問いも実行のときに結合で組み立てるので、特定の問いを優遇しません。NoSQL では結合がなく、読みたい形をあらかじめ作って格納しておくしかありません。そこで設計は、アクセスパターン、つまりアプリケーションが発行する問いの一覧の列挙から始まり、それぞれの問いを一回の取得で返せる形にデータを畳んで置きます。構造が先で問いが後だったリレーショナルに対し、問いが先で構造が後になるわけです。

問いの形に畳んで置く操作自体は第8章で見たものですが、地位が二つの点で違います。第一に、第8章の畳み込みは作り直せる導出でしたが、NoSQL の畳み込みは一次データそのもので、作り直す元がありません。第二に、複製の同期を DWH では変換パイプラインが担っていたのに対し、NoSQL ではアプリケーションのコードが負います。だから設計判断の中心は、何をどこまで複製し、その同期を誰がいつ行うかに置かれます。

集約指向という共通項は、トランザクションの範囲も定めます。集約とは、一つのキーの値や一つの文書のような、常に一緒に読み書きされるかたまりで、多くの製品で原子性の保証は一つの集約の中に限られます。だから集約の境界線は、原子的に更新したい範囲が内側に収まるように引きます。カートへの追加でそのカートが壊れないことは保証したいが、二人の顧客のカートをまたぐ原子性は要らない、という要領です。

なお、OLTP は更新異常を防ぐため正規化する、という第1章の整理と矛盾して見えますが、あれは結合を使えるリレーショナルの中の話です。結合を手放した NoSQL では、正規化された構造は問いに答えられない構造になるので、非正規化を受け入れた上で、更新時異常の抑え込みをアプリケーションが引き受ける配分になります。

引き換えに、問いに合わせて畳んだ構造は、畳んでいない問いに弱く、新しいアクセスパターンが現れたら、新しい畳み込みを足してデータを移し替えるか、全件走査で払うかになります。使い分けの軸はここにあります。問いを列挙し尽くせて、規模か遅延の要件がリレーショナルデータベースの限界を超えるなら NoSQL が合い、分析のように問いが開いているなら、結合で任意の問いに答えられるリレーショナルの中立性が効きます。

ここからは三つの型です。最も単純なのがキーバリューです。キーバリューストアは、キーから値への対応だけを保持します。操作はキーを指定した格納、取得、削除にほぼ限られ、値の中身をデータベースは解釈しません。設計はキー設計とほぼ同義で、原則は三つです。第一に、キーは問いの引数から組み立てます。顧客のカートを取る問いなら、顧客の識別子がキーになります。第二に、複数の種類のデータが同居するストアでは、キーに種別の接頭辞を付けてキー空間を仕切ります。第三に、値には集約を丸ごと入れます。部分的な読み書きはできないので、値の単位を、常に一緒に読み書きする単位と一致させるのです。適するのは、識別子で引き当てて丸ごと使うデータで、セッション、カート、キャッシュが典型です。限界も明快で、キー以外の手掛かりでは探せず、更新が30日ないカートの一覧のような条件の問いは、この型の外で答えることになります。

二つ目のドキュメントデータベースは、キーバリューの値に構造を認めた型です。値は文書、つまり JSON のような入れ子の構造を持つデータで、データベースが中身を解釈するため、文書内の項目への索引、条件付きの問い合わせ、一部だけの更新が効きます。設計の中心は、関連するデータを一つの文書に埋め込むか、識別子だけを持って別の文書を参照するかの判断で、目安は三つあります。一つ目は、一緒に読み書きするか。常に親と一緒に取得され更新されるデータは埋め込みます。一回の読みで済み、原子性も文書の中で効きます。二つ目は、単独で更新され共有されるか。複数の文書から使われるマスタのような事実は参照にします。埋め込むと、更新のたびに全文書を書き換えて回ることになるからです。三つ目は、際限なく増えるか。レビューやログのような上限のない一対多を埋め込むと文書が育ち続けるので、別の文書に切り出します。

実務では、参照にした上で、表示に要るタイトルなどの少数の属性だけを複製して埋め込む折衷に落ちることが多くなります。複製した属性の同期は自分の責務になりますが、例外が一つあります。その時点の値を写す複製は、そもそも同期してはならない複製です。注文明細に写した注文時点の単価は、マスタの価格が改定されても書き換えません。第5章で履歴として扱った時点の事実が、ここでは同期の要らない埋め込みとして現れます。なお、ドキュメントデータベースはスキーマレスと呼ばれますが、スキーマが消えたわけではなく、構造の合意はアプリケーションのコードに移り、検査は読み出す側で行われます。スキーマオンリードと呼ばれる考え方です。

三つ目の型はカラムナやカラム指向とも呼ばれ、第8章の列指向ストレージと紛らわしいのですが、両者は別物です。第8章のは表を列ごとに格納する物理配置の話、こちらは行キーの設計で問いに答える論理モデルの話で、本書では混同を避けてワイドカラムと呼びます。ワイドカラムのテーブルでは、行を識別するキーが二つの部分からなります。パーティションキーは、行をどのサーバに置くかを決め、クラスタリングキーは、同じパーティションの中の並び順を決めます。読み取りの基本形は、パーティションキーで一つのパーティションを引き当て、並び順の先頭から範囲を読むことです。設計原則はこの裏返しで、一覧を取る問いの主語をパーティションキーに、返したい並びをクラスタリングキーにし、テーブルは問いごとに作ります。同じデータでも、別の問いには別の並びの別テーブルを用意し、書き込み時に両方へ書くのです。この配分は、実装が追記中心で書き込みに強いから成り立ちます。適するのは、時系列のイベントやログのような、書き込みが激しく、直近の範囲を読む問いが決まっているデータです。

ここまではアプリケーション側の設計でした。視点をデータエンジニアへ戻します。畳み込みはアプリケーションの問いに向けて行われているので、書籍ごとの売上のような自由な切り口の集計はどの畳み込みにも収まらず、答えるには、本番ストアに負荷をかける全件走査しかありません。だから NoSQL を採用したシステムでも、分析はデータを DWH へ運んでから行います。分析基盤から見れば、ソースが一種類増えたわけです。取り込みには、新しい仕事が二つ加わります。一つは構造です。ソースの単位が文書やキーの値なので、まず JSON などの半構造化データの列としてロードし、リレーショナルの形に開く変換を基盤側で行います。もう一つは履歴です。文書もキーの値も上書きされ、削除までされるので、現在値しか残らないという第5章の問題が現れます。定期スナップショットか、変更の流れの購読、つまり CDC で変化を拾います。多くの製品が変更ストリームの機能を備えるため、CDC が第一候補です。

ここからは具体例です。第7章から計画されていた電子書籍ストアの開発が始まり、アプリケーションチームは、カートと読書進捗の書き込みが激しく規模の見通しも立てにくいことから、NoSQL の採用を検討しています。集約の境界と履歴の残り方はデータモデリングの問題そのものなので、データチームは設計レビューに加わり、同時に取り込みを設計します。

最初の作業は、ER 図を描くことではなく、アクセスパターンの列挙です。主要な問いは五つありました。顧客のカートを取得し更新する。注文を確定し内容を表示する。読書位置を記録し端末間で同期する。書籍ごと日ごとの売上を集計する。そして、更新が30日ないカートの一覧を出す。この時点で仕分けができます。後の二つは、識別子で引き当てる問いではなく条件と切り口の問いなので、分析基盤の仕事として預けておき、残った三つを、それぞれに合う型へ割り当てます。

カートは、ストアを開くたびに読まれ、商品を出し入れするたびに書き換わり、常に丸ごと読んで丸ごと描画されるので、カート全体を一つの集約としてキーバリューに置きます。キーは顧客 ID から組み立て、他の種類のキーと衝突しないよう、カートを表す接頭辞で仕切ります。値は、更新時刻と明細の配列を持つ JSON で、明細には ISBN と数量に加えて、タイトルと単価を複製して入れます。描画のたびに書籍マスタへ問い合わせないための複製で、価格改定との食い違いは、注文確定時に最新の価格を検証し直す手続きで吸収します。複製の同期を、確定時の検証一回に落とした形です。

注文は、確定で明細と支払いが原子的に書かれ、表示で常に全体が読まれるので、一件を一つの文書としてドキュメントデータベースに置きます。先ほどの目安のとおり、明細は埋め込みます。常に注文と一緒に読み書きされ、確定後は増えも変わりもしないからです。埋め込んだタイトルと単価は注文時点の値を保存する複製で、マスタが改定されても書き換えず、第5章の履歴の役目を兼ねます。一方、顧客は識別子の参照にとどめます。氏名は注文時点の事実ではなく、現在のプロフィールとして表示したい情報だからです。埋め込むと、改名のたびに過去の注文文書を書き換えて回るか、古い氏名を表示し続けるかの二択になります。

読書位置の同期は、書き込みの最も激しい問いです。ページがめくられるたびに端末が位置を送り、別の端末で開かれた瞬間に最新の位置を返す必要があります。時系列のイベントを積んで直近を読む形なので、ワイドカラムに置きます。テーブルは、顧客 ID と ISBN の組をパーティションキーにし、イベント時刻の降順をクラスタリングキーにします。この顧客のこの書籍の最新位置は、パーティションの先頭一行を読むだけで返り、範囲を伸ばせば読書履歴も新しい順に返せます。ここで、ライブラリ画面に購入済みの書籍を最近読んだ順に並べたい、という要件がもう一つ現れたとしましょう。このテーブルでは、パーティションが顧客と書籍の組で切られているので、書籍横断の並びはパーティションをまたいでしまい、答えられません。ワイドカラムの流儀は、顧客 ID だけをパーティションキーにし、最終閲覧時刻の降順を並びに持つ別テーブルを作り、進捗の書き込み時に両方へ書くことです。テーブルは問いごとという原則の実際の姿です。

最後に、預けてあった二つの問いに分析基盤で答えます。売上の集計は、注文文書の取り込みで答えます。注文文書は変更ストリームから日次で DWH の生テーブルへ、文書一件を一行、中身を JSON 型の一列として積みます。staging の規約は変えず、文書一件を一行のまま、JSON のパスを指定して型付けと改名だけを行う写しとします。明細の配列への展開は行数を変える操作なので intermediate に置き、配列を行に開きます。第8章で著者の配列を畳むのに使った道具が、ここでは開く向きで働くわけです。この先は新しい話ではなく、書籍のビジネスキーは ISBN と決めてあるので、電子書籍の注文は Hub と Link と Satellite を足して統合層に収め、マートの売上ファクトへ流します。指標の側では、電子書籍売上を宣言し、全社売上の派生の式に加えて定義を更新します。

放置カートの問いには、履歴の取り込みが要ります。カートは上書きされ、注文の確定や取りやめで削除されるので、どの時点にどんなカートが存在したかは本番ストアに残りません。そこでカートは変更ストリームから取り込み、キーごとの版を追記で積みます。最新の版の更新時刻が30日より古く、削除イベントの届いていないキーを選べば、放置カートの一覧になります。なお読書進捗は、ソース自体が追記のイベントなので、そのまま積めば済みます。

まとめます。NoSQL は、結合とトランザクションを手放す代わりに、分割と複製を素直に行える構造を選んだデータベース群で、設計はアクセスパターンの列挙から始まり、問いの形にデータを畳んで置きます。キーバリューはキー設計、ドキュメントは埋め込みと参照の境界、ワイドカラムは二部構成のキーと問いごとのテーブルが、それぞれの設計の中心でした。畳み込みは一次データなので、複製の同期はアプリケーションが引き受けます。そして分析の問いは畳み込みの外にあるので、変更ストリームで DWH へ運び、半構造化データを行に開き、履歴を積んで答えます。本章で本書の道具は出そろい、次の第11章は総合演習として、概念モデルから物理モデルまでを通しで設計します。以上で、第10章を終わります。
