対象章：[第5章 Slowly Changing Dimensions](../05-slowly-changing-dimensions.md)（[演習問題](../exercises/05-slowly-changing-dimensions.md)）

第5章、Slowly Changing Dimensions。この章では、ディメンションの属性が変わったときにどう対処するか、という問題を扱います。第4章の最後で確かめたとおり、これまでの顧客ディメンションは、ソースの写しを作り直すたびに全部の行が今の値へ上書きされていました。そのため、過去の注文に添えられる顧客の属性は、すべて現在の値になってしまいます。注文の時点の属性で過去を区切りたい、という問いに答えるには、変更を上書きで消すのではなく、履歴として残す設計が必要です。この対処法は、Kimball が Slowly Changing Dimensions、略して SCD として体系化しています。この章では SCD の各タイプの仕組みと使い分けを学び、第4章で予告したサロゲートキーの採番も具体化します。具体例では、書籍オンラインストアに会員ランク制度を導入し、当時の会員ランク別の売上に答えられる形へ、顧客ディメンションを作り直します。

まず、なぜディメンションの変更が問題になるのかを考えます。ディメンションの属性は不変ではありません。顧客は氏名やメールアドレスを変えますし、会員ランクは上下します。とはいえ、ファクトが毎日何千行と増えるのに比べれば、こうした変更はまれにしか起きません。slowly、つまりゆっくり変化する、という名前は、この頻度の非対称を指しています。

まれな変更が設計の問題になるのは、ファクトとディメンションで時間の性質が違うからです。ファクトの行は、いつ起きたかが確定した出来事の記録で、時点に固定されています。一方、これまでのディメンションの行は特定の時点に属さず、ただ、顧客42とはこういう人だ、と述べているだけです。顧客42の属性が変わると、この記述が変更前と変更後のどちらを指すのかが曖昧になり、過去のファクトにどの値を添えるべきか、という問いが生まれます。

どの値を添えるのが正しいかは、問いの側が決めます。現在の顧客へ案内を送るための抽出なら、添えるべきは今のメールアドレスで、当時の値に用はありません。逆に、当時の会員ランク別の売上を知りたいなら、今のランクを添えた集計は問いに答えていません。正解が問いごとに違う以上、対処法は選択肢の一覧という形を取り、Kimball はこれをタイプの番号で整理しました。大事なのは、タイプを選ぶ単位がテーブルではなく属性だ、ということです。同じ顧客ディメンションの中でも、メールアドレスは上書きし、会員ランクは履歴として残す、という混在が普通の姿になります。

では、タイプを順に見ていきます。Type 1 は、変更された属性を新しい値で上書きする方式です。履歴は残りません。第4章の顧客ディメンションは、結果として全属性が Type 1 になっていました。用途は二つあります。一つは誤記の訂正です。間違った値は履歴として残す価値がないので、上書きが正しい対処です。もう一つは、当時の値を問う問いが想定されない属性です。ただし、Type 1 が失うのは過去の値だけではありません。過去に作った集計の再現性も失われます。先月作ったレポートと同じ SQL を今月再実行すると、その間に値が変わった顧客の分だけ数字が動きます。それがデータの誤りではなく上書きの仕様であることを、利用者に説明できるようにしておく必要があります。なお、対になる方式として、変更をそもそも受け付けない Type 0 もあります。入会日のような、最初の値であることに意味がある属性は、ソースで値が書き換わっても元の値を守ります。

次が本章の主役、Type 2 です。当時の値で過去を区切る問いに答える方式で、属性が変わったら、行を書き換える代わりに新しい行を追加し、古い行はそのまま残します。単に履歴を持つディメンションと言えば、この方式を指すことが多いです。たとえば顧客42のランクが regular から gold に上がると、顧客42の行が二つできます。regular だった期間の行と、gold になってからの行です。

この形は三つの部品からできています。第一の部品はサロゲートキーです。同じ顧客IDを持つ行が二つできたので、顧客IDはもう一行を特定できません。主キーの役を降りて、同一顧客の行をまとめる自然キーとして残ります。顧客のある期間の姿、つまり一行を特定するキーは、DWH 側で新たに振るほかありません。これが第4章で予告した、履歴管理のためのサロゲートキーです。第二の部品は有効期間です。各行に、その姿が有効だった期間の開始と終了を持たせます。期間は、前の行の終わりと次の行の始まりが同じ値で接する、半開区間にそろえます。境界のちょうどその瞬間の出来事が、重複したり欠落したりする曖昧さをなくすためです。現在の行の終端はまだ決まっていないので、遠い未来を表す番兵値で埋めるか、NULL のままにします。第三の部品は現在行のフラグです。有効期間から導ける冗長な列ですが、今の姿だけが要る問い合わせを、単純な等値条件で書けるようにします。

Type 2 の要は、ファクト側の持ち方にあります。ファクトの行をロードするとき、出来事の時点で有効だったディメンション行を期間で探し、そのサロゲートキーを外部キーとして書き込みます。期間の照合はロード時に一度だけ済んでいるので、問い合わせではサロゲートキーの等値結合だけで当時の値が付き、期間の条件は現れません。また、現在の値で区切る問いにも Type 2 は答えられます。現在行のフラグで絞って自然キーで結合し直せば、全期間のファクトに今の属性が付きます。つまり Type 2 は、当時の値と現在の値の両方を出せる方式で、表現力の点では Type 1 の上位互換です。コストは行数ではありません。ディメンションは小さく変更もまれなので、行の増加が容量や速度の問題になることは少ないのです。実際のコストは運用にあります。変更を検出し、期間を重複や欠落なく維持し、ファクトへの割り当てを正しく保つという仕事が、パイプラインに恒久的に加わります。

Type 3 は、行ではなく列を足す方式です。属性の現在値の列に加えて、直前の値を保持する列を並べて持ちます。向いているのは、全体で一斉に一度だけ起きる変更です。典型は営業テリトリーの再編で、全期間を新旧どちらの体系でも集計したい、という要望に応えます。Type 2 は行が期間で分かれるため、同じ期間を新旧両方の切り口で見るこの問いには答えられません。裏返せば、顧客ごとにばらばらの時期に何度も変わる属性には向きません。保持できる履歴の深さが、設計時に固定されるからです。

Type 4 から 7 までは、ここまでの部品の応用と組み合わせです。Type 4 はミニディメンションと呼ばれ、頻繁に変わる属性群を切り出して別の小さなディメンションにし、ファクトから直接指します。購買頻度のスコアのように速く変わる属性を Type 2 にすると、行が増えすぎるための対処です。Type 5 から 7 は、Type 1 と 2 と 3 の混成です。番号を暗記する必要はなく、上書き、行の追加、列の追加、切り出しという部品を押さえておけば、問いに合わせた組み合わせとして読み解けます。

使い分けは、属性ごとに、どんな問いが届くかで決まります。当時の値で過去を区切る問いが届くなら Type 2、現在の値だけでよいか誤りの訂正なら Type 1、最初の値に意味があるなら Type 0、一斉の再編を新旧両方で見たいなら Type 3、変更が速すぎるなら Type 4、という具合です。表現力だけなら Type 2 が上ですが、全属性を無差別に Type 2 にはしません。運用の仕事が増えるうえ、誰も問わない属性の変更まで行を分割し、履歴がノイズとしてすべての問い合わせに付いて回るからです。履歴の問いが見込める属性に絞って Type 2 を適用し、残りを Type 1 に置くのが実務の均衡点です。

どのタイプを選ぶにしても、その前段には変更の検出という仕事があります。ソースシステムの多くは現在値しか持たず、変わったという事実を教えてくれません。ソースの更新イベントを流してもらえるなら、これは Change Data Capture、CDC と呼ばれますが、そこから履歴を組み立てられます。もらえないなら、DWH 側で定期的にソースを写し、前回の写しと比べて差分を見つけるほかありません。この比較では、取得の間隔より細かい変化は捉えられません。日次の取得なら、一日のうちに二回変わった中間の値は失われます。dbt はこの定期取得と比較を、snapshot という機能として備えています。

ここから具体例です。書籍オンラインストアに会員ランク制度が導入されたとしましょう。ソースの顧客テーブルに会員ランクの列が追加され、購買実績に応じて値が変わります。マーケティングからは、ランク別の売上を知りたい、ただし今のランクではなく注文した当時のランクで区切ってほしい、という問いが届いています。方針を属性ごとに決めます。会員ランクは、当時の値で区切る問いが現に届いているので Type 2 とします。氏名とメールアドレスは、過去の値で売上を区切る問いが考えにくいので、Type 1 のままです。

最初の仕事は変更の検出で、dbt の snapshot を使います。snapshot は、実行のたびにソースの現在値を前回までの結果と比較し、指定した列が変わっていた行について、古い版の有効期間を閉じて新しい版の行を追加します。Type 2 の行の追加を、汎用の仕組みとして肩代わりしてくれるわけです。設定では、比較する列に会員ランクだけを指定します。Type 1 と決めた氏名やメールアドレスの変更で、版を増やさないためです。snapshot の結果には、各版の有効期間の列が自動で付きます。ただし、snapshot には二つの限界を織り込んでおきます。第一に、履歴が残るのは運用を始めた後だけで、それ以前の変更は遡って復元できません。第二に、実行の間隔より細かい変化は失われます。この例では日次実行とし、ランクの変更を日単位で捉えられれば問いに足りると判断しました。

次に、snapshot の結果から顧客ディメンションを組み立てます。このモデルには、概念の解説で述べたことが三つ現れます。一つ目はタイプの混在です。Type 2 の会員ランクと有効期間は snapshot から取り、Type 1 の氏名とメールアドレスは、現在のソースの写しから結合で取ります。過去の版の行にも、氏名とメールアドレスは常に今の値が付きます。二つ目はサロゲートキーの採番です。自然キーと版の開始時刻の組からハッシュ値を計算して振ります。ロードのたびに同じ入力から同じキーが再現されるので、テーブルを作り直してもファクト側の参照が壊れません。三つ目は期間の番兵値です。現在の版の終端を NULL のままにせず、未来側の番兵値で埋め、後続の期間条件を単純な比較で書けるようにします。もう一つ細かい手当てとして、最初の版の開始時刻は、過去側の番兵値まで開いておきます。そのままでは snapshot を始める前の注文がどの版の期間にも当たらず、宙に浮くからです。導入前の期間は最初の写しの値で代表させると決めるわけですが、その期間のランクが正確には分からないという事実自体は、この手当てでは消えません。

ファクトのロードでは、顧客IDが一致し、かつ注文時刻がその版の有効期間に収まるディメンション行を探して、そのサロゲートキーをファクトに書き込みます。第4章のクエリと変わるのは、顧客への結合条件だけです。期間の照合はこのロードの一度きりで、問い合わせ側には現れません。顧客IDも自然キーとして残しておきます。現在の属性で区切る問いと、ソースとの突き合わせに使うためです。

こうして、届いていた問い、注文当時のランク別の売上は、ファクトとディメンションをサロゲートキーで等値結合し、ランクごとに金額を合計するだけの単純なクエリで書けます。同じテーブルで、今 gold の顧客が過去に上げた売上の合計、という現在値の問いにも答えられます。こちらは現在行だけに絞って、自然キーで結合し直します。二つの問いの違いが、どちらのキーで結合するかの違いとして現れています。当時の姿はサロゲートキーで、今の姿は自然キーで引く。これが Type 2 ディメンションの使い方の要領です。

最後に検査です。Type 2 が加えた設計の宣言は、各顧客の有効期間は重複も欠落もなく一列に並ぶ、というものです。期間が重複していると、ロードの期間結合で一つの明細が複数のディメンション行に当たり、ファクトの行が静かに複製されます。期間に欠落があると、その間の注文はどの行にも当たらず、結合で静かに落ちます。どちらも集計を黙って狂わせる事故です。サロゲートキーの一意性や参照整合性は、第4章と同じく yml の宣言で検査します。期間の重複のような行またぎの条件は列単位の宣言では書けないので、違反した行だけを返す SQL を直接書いて、結果がゼロ行なら合格とする検査にします。dbt では singular test と呼びます。snapshot が正しく動いている限り宣言は破れないはずですが、そのはずを検査に落としておくのが、これまで続けてきたロード後検査の方針です。

章を閉じる前に、一つ視野を広げておきます。本章の設計は、履歴の獲得を DWH の入り口の snapshot に、履歴の表現をスタースキーマのディメンションに置きました。顧客ディメンションを注文以外のプロセスとも共有するなら、履歴の設計は共有される一枚の上で一度だけ行いたくなります。DWH 全体をどんな層で組み上げるかは、第6章で Inmon と Kimball の方式を対比して扱います。変更の保存そのものをモデリングの中核に据える流儀は、第7章の Data Vault で扱います。

まとめます。ディメンションの属性はまれに変わり、過去のファクトにどの値を添えるべきかは問いの側が決めるので、対処はタイプの一覧になります。上書きの Type 1、保持の Type 0、行を追加する Type 2、列を追加する Type 3、切り出しの Type 4 という部品を、属性ごとに使い分けます。主役の Type 2 は、サロゲートキー、有効期間、現在行フラグの三つの部品でできていて、ロード時に期間を照合してサロゲートキーをファクトへ書き込むことで、当時の値はサロゲートキーで、現在の値は自然キーで引けるようになります。コストは行数ではなく、変更の検出と期間の維持という運用にあり、dbt では snapshot と singular test がその仕事を支えます。以上で、第5章を終わります。
