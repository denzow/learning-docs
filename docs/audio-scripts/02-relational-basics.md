# 第2章 リレーショナルモデルの基礎（読み上げ原稿）

第2章、リレーショナルモデルの基礎。第1章では、論理モデルとは概念モデルを特定のデータモデル体系に写したものだと説明し、その体系として主にリレーショナルモデルを使うと述べました。この章では、そのリレーショナルモデルの側を扱います。テーマは三つです。業務をエンティティと関係の形で捉える ER モデリング、行を一意に特定するためのキー設計、そしてデータに構造の約束を守らせる制約です。これらはもともと業務システム側、つまり OLTP 側のデータベース設計の技法として発展してきました。しかしデータエンジニアにとっては、ソースシステムから届くデータを読み解くための語彙でもあります。取り込んだテーブルのどの列が主キーで、どのテーブルと外部キーで結ばれているか。それが分からなければ、結合も重複排除も設計できません。さらに、データウェアハウス側には制約が強制されないという事情があり、OLTP ではデータベース管理システムに任せられた整合性の保証を、パイプラインの設計者が自前で組み込むことになります。この事情は章の後半で扱います。

まず、リレーショナルモデルそのものから始めます。テーブル、行、列という言葉は日常的に使いますが、その背後には数学に基づく理論があります。リレーショナルモデルは、1970年にコッドが提案したデータモデル体系で、すべてのデータをリレーションと呼ばれる構造だけで表します。リレーションは、属性の値の組、つまりタプルの集合です。SQL の世界では、リレーションがテーブルに、タプルが行に、属性が列に、ほぼ対応します。

理論の細部よりも、集合であるという性質から何が導かれるかが実務に効いてきます。集合の要素に順序はありませんから、行の並び順に意味を持たせるわけにはいきません。また、集合は同じ要素を二つ含みませんから、行は値によって互いに区別できなければなりません。つまり、この行はどれか、を特定する手段は、行の中の値しかないのです。それを保証する仕組みとして、キーが必要になります。

テーブルどうしの関連も、ポインタや位置ではなく、値で表します。あるテーブルの列の値が、別のテーブルのキーの値と一致すること。それが、行から行への参照になります。外部キーとは、この値の一致による参照のことです。

次に、ER モデリングです。リレーショナルモデルが、写した後の構造を定めるのに対して、業務を写す前に捉える方法を与えるのが ER モデリングです。1976年にピーター・チェンが定式化した手法で、業務を三つの部品で記述します。一つめはエンティティ。業務で識別して管理したい対象で、顧客、書籍、注文などが該当します。二つめは属性。エンティティが持つ値で、顧客の氏名やメールアドレスなどです。三つめはリレーションシップ。エンティティ間の業務上の関連で、顧客が注文を行う、といった事実を表します。

リレーションシップには、カーディナリティを定めます。一方のエンティティ一件に対して、他方が何件対応するかで、一対一、一対多、多対多の三種類に分かれます。あわせて、対応がゼロ件の場合を許すかどうか、これをオプショナリティと呼びますが、これも記します。第1章の ER 図に込めた、一つの注文は一人の顧客に属する、注文は少なくとも一つの明細を含む、という事実は、カーディナリティとオプショナリティの表現だったわけです。

このうち多対多だけは、リレーショナルモデルへそのまま写せません。外部キーの列は一行につき一つの値しか持てず、リレーショナルモデルは列に値の集合を入れることを認めないからです。この原則は、第3章で扱う第1正規形につながります。では多対多はどうするか。両側への外部キーを持つ連関エンティティ、交差テーブルとも呼びますが、これを間に挟んで、二つの一対多に分解します。具体例のところで、著者と書籍を題材にこの分解を見ていきます。

三つめのテーマ、キー設計に移ります。行を特定する手段は値しかない、と述べました。では、どの列に、あるいはどの列の組み合わせに、行の特定を担わせるか。それを決めるのがキー設計です。用語を整理しておきます。行を一意に特定できる、それ以上列を減らせない列の組を、候補キーと呼びます。候補キーの中から代表として選んだ一つが、主キーです。主キーに選ばれなかった候補キーは代替キーと呼び、一意性制約で守ります。複数の列からなるキーは、複合キーと呼びます。

主キーの選定で繰り返し現れる論点が、自然キーとサロゲートキーの選択です。自然キーは、業務の世界にもともと存在する識別子です。ISBN、社員番号、メールアドレスなどが該当します。一方サロゲートキーは、行の識別のためだけにシステムが採番する値で、業務上の意味を持ちません。主キーに向くのは、値が変わらず、NULL にならず、確実に一意である列です。自然キーは、この条件を満たさないことが多いのです。業務上の識別子は、業務の都合で値が変わります。メールアドレスの変更や、組織再編に伴う社員番号の振り直しを思い浮かべてください。また、業務ルールには例外がつきものです。識別子が付与されない対象や、重複の混入があり得ます。そのため実務では、主キーにはサロゲートキーを使い、自然キーは代替キーとして一意性制約で守る、という設計が広く採られています。ただし、連関エンティティのように、親のキーの組で自然に識別できるテーブルを複合主キーのままにする選択も普通です。

四つめの概念が、制約です。キーや参照の定義は、それだけでは設計図の上の約束にすぎません。実際のデータにその約束を守らせる仕組みが制約で、DDL で宣言しておくと、以後はデータベース管理システムが違反する書き込みを拒否してくれます。主要な制約は五つあります。主キー制約は、指定した列が一意で NULL を含まないことを保証します。一意性制約は、値が重複しないことを保証し、代替キーを守ります。NOT NULL 制約は、列に必ず値が入ることを保証します。外部キー制約は、参照先の行が存在することを保証するもので、参照整合性とも呼びます。CHECK 制約は、行の値が条件式を満たすこと、たとえば数量が正であることを保証します。

制約の価値は、守れる範囲の広さにあります。アプリケーションのコードで検証しても、データベースへ書き込む道はほかにもあります。別のアプリケーション、管理者の手作業、移行スクリプトなどです。制約はデータベース管理システム自身が検査するため、どこからの書き込みにも同じ検査が適用され、不正なデータの混入を書き込みの時点で止められます。

ただし、データエンジニアが主戦場とするクラウドデータウェアハウスでは、この前提が崩れます。BigQuery や Snowflake は、主キーや外部キーの宣言を受け付けますが、既定ではそれを強制しません。行単位の検査は大量データのロードを遅くするため、検査を省いて取り込みを速くする、という設計判断です。したがってデータウェアハウスでは、一意性や参照整合性を、書き込み時に拒否するのではなく、ロード後の検査で検出する形で担保することになります。

ここからは具体例です。第1章と同じ、書籍のオンラインストアを題材にします。前章の四つのエンティティ、顧客、注文、注文明細、書籍では、関係はすべて一対多で、キーの選定にも迷う余地がありませんでした。そこで、多対多の分解と自然キーの採否が現れるように、書籍のまわりに著者を加えて広げます。

書籍と著者の関係を、業務の言葉で確かめてみます。一冊の書籍は、共著であれば複数の著者を持ちます。一人の著者は、複数の書籍を書きます。つまり多対多です。概念モデルでは、そのまま多対多として描いてかまいません。論理モデルへ写す段階で、この多対多を連関エンティティに分解します。テーブルとしては三つになります。著者テーブルは、著者 ID を主キーに、名前を持ちます。書籍テーブルは、書籍 ID を主キーに、ISBN、タイトル、定価を持ちます。そして連関エンティティにあたる書籍著者テーブルが、書籍 ID と著者 ID の複合主キーを持ち、両方への外部キーで二つの一対多を作ります。連関エンティティは、関係を表すためだけの存在に見えますが、関係そのものの属性を持てる場所でもあります。この例では、著者の表示順という列を書籍著者テーブルに置いています。表示順は、書籍にも著者にも属さず、この書籍とこの著者の対応に属する情報なので、ここに置くほかないのです。

次に、書籍の主キーの選定です。書籍には ISBN という有力な自然キーがあります。出版流通で世界的に使われる識別子で、一冊に一つ付与される建前ですから、一意で不変に見えます。主キーを ISBN にすれば、サロゲートキーの採番も要らなくなります。しかし、主キーの条件である不変、非 NULL、一意に照らすと、ISBN は三つとも満たさない場合があります。まず、自費出版物や非売品には ISBN が付与されないことがあり、これらを扱うなら ISBN の列は NULL を許す必要があります。また、ISBN は2007年に10桁から13桁へ移行しており、値が世界規模で振り直された歴史を持ちます。さらに、規格上は禁止されているものの、絶版書の ISBN が別の書籍に再利用された事例も知られています。こうした例外は業務ルールの側で生まれるため、テーブル設計の側では防げません。そこで、書籍の主キーはサロゲートキーの書籍 ID とし、ISBN は代替キーとして一意性制約で守ります。一方、著者には、同姓同名を区別できる自然キーがそもそも存在しませんから、サロゲートキーの著者 ID が最初から唯一の選択肢になります。書籍著者テーブルは、親二つのキーの組がそのまま候補キーなので、複合主キーのままとします。

この決定を、制約として DDL に落とします。原文には三つのテーブルを作る SQL が載っていますが、要点は、それぞれの制約がどんな不正データを止めるか、という対応づけです。ISBN の一意性制約は、同じ ISBN の二重登録を止めます。なお、標準 SQL の一意性制約は NULL を比較の対象にしないため、ISBN のない書籍が何冊あっても違反にはなりません。書籍著者テーブルの複合主キーは、同じ書籍に同じ著者を二度対応づけることを止めます。書籍 ID と表示順の組に付けた一意性制約は、一冊の中で表示順が衝突することを止めます。外部キー制約は、存在しない書籍や著者への対応づけと、対応が残っている書籍や著者の削除を止めます。CHECK 制約は、負の定価やゼロ以下の表示順のような、データ型だけでは防げない値を止めます。

ひとつ、この DDL では表現できていないルールがあります。書籍は少なくとも一人の著者を持つ、というカーディナリティの下限です。ここまでの制約はいずれも、書き込まれる行とその参照先を検査するものです。書籍の各行に対して書籍著者の行が存在する、という逆向きの存在検査を宣言する標準的な手段はありません。この種のルールは、アプリケーション側の検証か、次に述べるロード後の検査で担保します。

最後に、このデータがデータウェアハウスに取り込まれた後を考えます。クラウドデータウェアハウスは主キーや外部キーを強制しませんから、同じ整合性をロード後の検査として書き直すことになります。dbt では、モデルに対する宣言的なテストとして記述できます。書籍 ID にユニークとノットヌルのテストを宣言すれば主キー制約に相当し、書籍著者テーブルの書籍 ID や著者 ID に、参照先のモデルを指すリレーションシップスのテストを宣言すれば外部キー制約に相当します。dbt はこの宣言を、違反する行を数える SQL に変換して実行し、違反があればテストの失敗として報告します。制約とテストは、同じルールを検査しますが、働くタイミングが違います。制約は書き込みの時点で拒否するため、不正データはそもそも入りません。テストはロードの後に検出するため、不正データは一度入ってから見つかります。データウェアハウスでは後者しか選べない以上、テストをパイプラインに組み込み、違反を検出したら下流への反映を止める、という運用までがセットになります。なお、dbt のテストは任意の SQL でも書けるため、DDL では表現できなかった、著者のいない書籍が存在しないという検査も、ここでなら担保できます。

まとめます。リレーショナルモデルは、データをタプルの集合であるリレーションで表す体系で、集合であるがゆえに、行の特定はキーが、テーブル間の参照は値の一致による外部キーが担います。ER モデリングは、業務をエンティティ、属性、リレーションシップで捉え、カーディナリティを定めます。多対多は連関エンティティで二つの一対多に分解します。キー設計では、不変、非 NULL、一意という条件から、主キーにはサロゲートキーを使い、自然キーは代替キーとして守るのが実務の定石でした。そして制約は、こうした約束をデータベース管理システムに強制させる仕組みですが、クラウドデータウェアハウスでは強制されないため、dbt のテストのようなロード後の検査と、違反時に下流を止める運用で整合性を担保します。以上で、第2章を終わります。
