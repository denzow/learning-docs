# 第6章 DWH アーキテクチャ（読み上げ原稿）

対象章：[第6章 DWH アーキテクチャ](../06-dwh-architecture.md)

第6章、DWH アーキテクチャ。前の章の最後で、履歴の設計をどこに置くかという問いが、テーブル一枚の設計を超えることを確かめました。この章では、どのテーブルを共有し、ソースから利用者までの間にどんな層を並べるかという、データ基盤全体の組み立てを考えます。これを DWH アーキテクチャと呼びます。この問いには、DWH の草創期に確立された二つの古典的な回答があります。Bill Inmon の方式と、Ralph Kimball の方式です。この章では両者の構造と対比、そして現代のクラウド DWH と dbt の実務が両者をどう組み合わせているかを扱います。具体例では、書籍オンラインストアに出荷のプロセスを追加します。

まず、言葉の定義から始めます。DWH という概念を定式化した Inmon は、データウェアハウスを、意思決定の支援のための、主題指向で、統合済みで、時系列で、不揮発なデータの集合と定義しました。四つの形容には、それぞれ設計上の意味があります。主題指向とは、注文システム、倉庫システムといったアプリケーションの単位ではなく、顧客、書籍、注文といった業務の主題の単位でデータを編成することです。統合済みとは、ソースシステムごとに食い違う ID の体系やコード、単位、表記を、格納する前にそろえることです。時系列とは、現在の状態だけでなく履歴を保持することで、第5章で学んだ SCD はこの性質をディメンションの上で実現する技法でした。不揮発とは、ロードした行を業務アプリケーションのようには書き換えず、追記と読み取りだけで運用することです。この四つのうち統合済みだけは、ここまでの具体例に現れる機会がありませんでした。ソースが注文システム一つだけだったからです。この章の具体例で、初めて二つ目のソースを迎えます。

一方、データマートは、特定の部門や分析用途のための、範囲を絞ったデータの集合を指します。マーケティングが見る売上分析のスタースキーマ、物流チームが見る出荷分析のスタースキーマ、という単位です。分析者や BI ツールが日々問い合わせる相手はデータマートであり、この点はどの流儀でも変わりません。アーキテクチャ論が分かれるのは、ソースとマートの間に何を置き、マート同士の整合をどう保つかです。

議論の出発点は、アーキテクチャなしにマートだけを積み上げるとどうなるか、です。部門ごとにソースから直接データを抽出し、それぞれの変換でそれぞれのマートを作る形を、独立データマートと呼びます。一番手軽に始められますが、マートが増えるにつれて、同じはずの数字が食い違い始めます。経営会議で、営業のいう売上とマーケティングのいう売上が合わない、という広く知られた症状です。この食い違いは偶然のバグではなく、構造から生まれます。キャンセルされた注文を数えるか、送料や割引をどう扱うか、月の区切りを注文日と出荷日のどちらで取るか。こうした決定が、マートの数だけ別々に下されるからです。この状態はサイロと呼ばれ、Inmon と Kimball のどちらもが防ごうとした共通の相手です。つまり二つのアーキテクチャは、ソースの統合と共通の定義を一度だけ行う場所をマートの手前に用意する、という同じ処方を共有しています。分かれるのは、その場所の形です。

Inmon の回答は、中央に一つのエンタープライズデータウェアハウス、略して EDW を築くことです。全社のデータを主題別に編成し、履歴を持ち、おおむね第3正規形に正規化してモデリングします。利用者は EDW を直接問い合わせません。部門や用途ごとのデータマートを EDW から派生させ、利用者にはマートだけを見せます。マートの形はスタースキーマでかまいません。中央の層を正規化する理由は、EDW の役割から出てきます。EDW の役割は特定の分析の問いに答えることではなく、将来のどんなマートの源にもなることです。分析の問いは移ろうので、どれかの問いの形に寄せた構造は、次のマートを作るときに足かせになります。問いから独立に、業務の事実を重複なく一度だけ持つ形として、正規化が選ばれるのです。進め方はトップダウンになります。まず全社のデータモデルを設計し、EDW を構築し、そのうえでマートを切り出します。統合と履歴の設計が一箇所に集まる見返りに、先行投資は大きく、EDW が完成するまで分析者の手元には何も届きません。

Kimball の回答は、別立ての正規化された中央層を作らないことです。ビジネスプロセスごとにスタースキーマを作っていき、その集合をそのまま DWH とします。中央層なしでサイロを避けられるのは、統合の仕事を適合ディメンションが引き受けるからです。注文のファクトも出荷のファクトも同じ顧客ディメンションと日付ディメンションを参照していれば、どのマートでも顧客の区分と月の区切りが同じになり、プロセスをまたいだ数字の突き合わせが成り立ちます。共通の定義は、中央の層にではなく、共有されるディメンションそのものに宿ります。この構造をバスアーキテクチャと呼びます。適合ディメンションが共通規格のバスであり、新しいプロセスのスタースキーマは、既存のディメンションに接続する形で追加されていきます。計画の道具として、Kimball はバスマトリクスを使います。行にビジネスプロセスを、列にディメンションを並べ、どのプロセスがどのディメンションで記述されるかを印で埋めた表です。複数の行から印の付く列が、適合させるべきディメンションを教えてくれます。表を埋める作業は全社を見渡して行いますが、実装はプロセス一つずつでよく、最初のスタースキーマが完成した時点から分析者は使い始められます。この進め方がボトムアップと呼ばれます。代償は、適合を守り続ける規律です。目先の都合で専用の顧客テーブルを立てたスキーマは、その時点でバスから外れ、独立データマートに逆戻りします。

二つのアーキテクチャは、かつて盛んに論争されました。しかし対立の図式だけで覚えると、共有されているものを見落とします。統合と共通の定義を一度だけ行うこと、利用者に見せる形はディメンショナルであること、履歴を共有の場所で管理すること。この三点で両者は一致しています。争点は、正規化された中央層を、利用者向けの層とは別に持つ価値があるか、という一点に絞られます。どちらに寄せるかは組織の条件で決まります。ソースシステムの数が多く食い違いが深いほど、中央層の価値は上がります。ソースが少なく、目の前の分析要望に早く応えたいほど、バスの軽さが効きます。

現代のクラウド DWH と dbt の実務は、どちらか一方を純粋に採るより、両者の要素を層として並べる形に落ち着いています。論争の当時、EDW とマートは別々のサーバに立つ別々のシステムであることが多く、中央層を持つかどうかは大きな投資判断でした。クラウド DWH では、どの層も同じ製品の中のスキーマにすぎず、層を一つ増やすことは dbt のディレクトリを一つ増やすことでしかありません。dbt Labs が推奨するプロジェクト構成は、staging、intermediate、marts の三層です。staging にはソースのテーブルと一対一のモデルを置き、列名と型の整えやコードの読み替えを行って、ソースごとの癖を吸収します。intermediate には、複数の staging モデルにまたがる共通の変換を必要に応じて置きます。marts は利用者に見せる層で、ファクトテーブルと適合ディメンションを置きます。この構成は、marts が Kimball のバスをそのまま実装しつつ、EDW が担っていた仕事の一部、つまりソース差異の吸収と履歴の獲得を、staging と snapshot が引き受けた混成の形として読めます。

ここからは具体例です。書籍オンラインストアに、二つ目のビジネスプロセスとして出荷を加えます。出荷を記録しているのは注文システムではなく、倉庫で使われている倉庫管理システムです。在庫が足りなければ出荷は分割され、遅れもします。だから物流チームからは、書籍ごとに注文された冊数と出荷された冊数を月別で並べたい、差が開いている書籍は欠品か出荷漏れを疑いたい、という問いが届いています。この問いはプロセスをまたいでおり、単一のスタースキーマの中では答えられません。

出荷の設計に入る前に、バスマトリクスで全体を見ます。日付、顧客、書籍のディメンションにはすでに注文のプロセスが印を付けています。だから出荷のスキーマはこの三つを新設せず、既存のディメンションに接続します。新しいのは配送業者だけで、出荷専用のディメンションとして新設します。つまりこの拡張で増える実装は、出荷ファクトと配送業者ディメンションの二つだけです。グレインは出荷明細一行、つまり一回の出荷に含まれる書籍一種ごとに一行と宣言し、メジャーは出荷冊数とします。

そして、予告していた統合の仕事が、ここで初めて実際に生じます。倉庫管理システムは、書籍を注文システムの内部連番では識別していません。倉庫の現場で現物との突き合わせに使うのはバーコード、すなわち ISBN だからです。ここで第2章の決定が効いてきます。書籍テーブルを設計したとき、ISBN は主キーには不適として退けつつ、代替キーとして一意性制約で守っていました。ソースをまたいで同じ書籍を指せる共通の語彙は、システム内部の連番ではなく、この業界標準の自然キーなのです。読み替えは staging 層で行います。出荷明細の staging モデルで、ISBN をキーに書籍の staging モデルと結合し、内部の書籍 ID に引き当てるクエリを書きます。これ以降のモデルは、出荷明細を注文システムと同じ語彙で扱えます。

出荷ファクトテーブルは、ここまでの章で作った部品に接続するだけで組み上がります。出荷明細とヘッダ、注文の staging モデルを結合し、顧客については第5章のパターンそのままに、有効期間を照合してサロゲートキーを引きます。照合に使う時刻は注文時ではなく出荷時です。このファクトが記録する出来事が出荷だからです。このモデルで注目すべきは、書いていないことのほうです。日付、顧客、書籍のディメンションには、変更が一切ありません。出荷のスキーマは、注文のスキーマが参照しているのと同じディメンションの行を参照します。これがバスに接続するということです。

では、届いていた問いに答えます。注文と出荷という別々のファクトの数字を並べるとき、二つのファクトテーブルを直接結合するわけにはいきません。グレインが違うからです。一件の注文明細が分割出荷で複数の出荷明細に対応すると、直接の結合では注文冊数が出荷明細の数だけ複製され、合計が静かに水増しされます。定石は、各ファクトを共通のディメンション属性でそれぞれ集計してから、集計結果同士を突き合わせることです。この操作をドリルアクロスと呼びます。クエリとしては、まず注文ファクトを年、月、書名で集計して月別の注文冊数を出し、次に出荷ファクトを同じ年、月、書名で集計して月別の出荷冊数を出し、最後に二つの集計結果を完全外部結合で突き合わせます。完全外部結合にするのは、問いの狙いが差にあるからです。注文だけあって出荷のない組は欠品の疑い、出荷だけあって注文のない組はデータの異常であり、どちらも落とさずゼロと並べて見せたいのです。この問い合わせが成り立つ条件が、この章の主題そのものです。突き合わせのキーになる年、月、書名は、両側とも同じ日付ディメンションと書籍ディメンションから来ています。もし出荷のマートが書籍を ISBN のまま持っていたら、この結合は組にならない行を量産し、あらゆる書籍が欠品と異常に見える表が返ります。独立データマートの数字が合わないという症状は、この壊れた突き合わせの姿であり、適合ディメンションはそれを防ぐ仕組みとしてここで働いています。

この章の設計宣言も、これまでの章と同じように検査へ翻訳できます。ソース側では、出荷明細の ISBN に参照整合性のテストを置き、注文システムの知らない ISBN が倉庫側に現れたら入り口で検出します。読み替えの結合で明細が静かに落ちる前に捕まえるためです。marts 側では、出荷ファクトの各キーに、既存の日付、書籍、顧客ディメンションへの参照整合性テストを置きます。テストの参照先が新設のテーブルではなく既存のディメンションを指していること自体が、バスへの接続の宣言として読めます。

最後に、出来上がった構成を対比に照らして振り返ります。利用者に見せる marts 層は、プロセス別のスタースキーマを適合ディメンションでつないだ、Kimball のバスそのものです。一方で、staging 層はソースごとの癖を吸収し、snapshot は履歴を獲得しており、EDW が担っていた仕事の一部が入り口の層に移っています。正規化された明示的な統合層は、まだありません。ソースが二つ、重なる主題が書籍と顧客だけの規模では、staging の読み替えで足りるからです。この判断は規模とともに変わります。ソースシステムが増えて、同じ顧客と同じ書籍が四つのシステムに別々の姿で現れるようになれば、突き合わせのロジックは staging のあちこちに散らばって膨らみます。そのときが、主題ごとの統合を明示する中間の層を立てる時機です。その層のモデリング法の一つを、第7章の Data Vault で扱います。

まとめます。DWH アーキテクチャとは、ソースから利用者までの間にどんな層を並べ、どのテーブルを共有するかの決定でした。独立データマートの数字の食い違いを防ぐため、Inmon は正規化された中央の EDW を置き、Kimball は適合ディメンションのバスでスタースキーマ群をつなぎました。両者は、統合と共通の定義を一度だけ行うという処方を共有しており、現代の dbt の三層構成は両者の混成として読めます。具体例では、出荷のプロセスをバスに接続し、ISBN による統合を staging で行い、ドリルアクロスでプロセス横断の問いに答えました。以上で、第6章を終わります。
