# 第3章 正規化（読み上げ原稿）

対象章：[第3章 正規化](../03-normalization.md)

第3章、正規化。この章では、テーブルの構造そのものから重複と矛盾を取り除く理論である正規化を学びます。前半では、正規化が防ごうとする更新異常と、判定の道具である関数従属、そして第1正規形から第5正規形、ボイス・コッド正規形までの系列を扱います。後半では逆に、分析用の設計であえて正規化を崩す、非正規化の判断基準を扱います。

まず、前の章とのつながりから話します。第2章では、キーと制約で不正な書き込みを止める仕組みを扱いました。しかし制約が検査できるのは、書き込まれる行と、その参照先までです。テーブルの構造が、同じ事実を複数の行に重複して記録させる形になっていると、重複した記録どうしが一致し続けるというルールを宣言する標準的な制約はなく、矛盾の混入を構造の外からは止められません。であれば、重複を生まない構造をはじめから選べばよい。どの属性をどのテーブルに置けば重複が生じないか、その判定基準を与えるのが正規化の理論です。

正規化が防ごうとする事故を、先に押さえます。テーブルの構造が同じ事実を複数の行に記録させるとき、三種類の異常が起きます。一つ目は修正異常です。事実が変わったとき、重複したすべての行を更新しなければならず、一部だけが更新されると矛盾が残ります。二つ目は挿入異常です。記録したい事実が単独では行の形にならず、別の事実がそろうまで挿入できません。三つ目は削除異常です。ある事実を消すための行の削除が、残しておきたい別の事実まで一緒に消してしまいます。三つをまとめて更新異常と呼びます。異常の原因は、行の単位と事実の単位のずれにあります。一つの行が、顧客の連絡先、注文の日時、書籍の題名といった、種類の違う複数の事実を運んでいると、事実ごとに発生や変更のタイミングが違うため、重複と欠落が避けられません。正規化は、一つの事実が一箇所にだけ記録されるようにテーブルを分解し、このずれをなくす技法です。

分解の判断には、どの属性がどの属性によって決まるかを書き出す道具が要ります。これが関数従属です。ある属性の組の値が決まれば、別の属性の値がただ一つに決まるとき、後者は前者に関数従属すると言います。たとえば書籍のテーブルでは、書籍の ID が決まれば題名が決まるので、題名は書籍 ID に関数従属します。関数従属は、手元のデータを眺めて見つけるものではなく、業務ルールの写しです。いまのデータでたまたま重複がないことと、業務ルールとして常に成り立つことは別で、正規化の根拠になるのは後者だけです。キーもこの言葉で言い直せます。候補キーとは、テーブルのすべての属性を関数従属させる、それ以上列を減らせない属性の組のことです。さらに、正規形の判定では従属の形を二つ区別します。複合の候補キーの一部分だけに従属することを部分関数従属と呼びます。キーから非キー属性へ、そこからさらに別の非キー属性へという連鎖を通じた従属を、推移的関数従属と呼びます。

正規形の系列の出発点が第1正規形です。すべての属性の値が、それ以上分解して扱わない単位、つまり原子的な値であり、繰り返しの構造を持たないことを求めます。複数の著者名をカンマ区切りで一つの列に詰めたり、電話番号の一、二、三のような繰り返しの列を作るのが典型的な違反です。これが問題になるのは、値の中身に SQL の機能が届かなくなるからです。カンマ区切りの著者名から特定の著者を探すには文字列処理が必要になり、著者に対する一意性制約も外部キーも宣言できません。

第2正規形と第3正規形は、非キー属性が持つ余計な関数従属を外していく段階です。第2正規形は、非キー属性が候補キーに部分関数従属しないことを求めます。主キーが単一の列なら部分従属は起きようがないので、問題になるのは複合キーのテーブルだけです。第3正規形は、さらに推移的関数従属もないことを求めます。どちらの違反も、キー全体以外の何かで決まる事実が行に紛れ込んでいることを意味します。解消のしかたは共通で、その従属の左辺、つまり決定項を主キーとする別のテーブルへ属性を移します。標語では、非キー属性は、キーに、キーの全体に、キーだけに従属せよ、とまとめられます。

第3正規形の定義には見逃しが残っています。禁じたのは非キー属性の従属だけで、候補キーを構成する属性への従属は対象外だからです。ボイス・コッド正規形、略して BCNF は、この穴を塞ぎます。自明でないすべての関数従属について、その決定項がいずれかの候補キーを丸ごと含むことを求めるのです。もっとも、第3正規形を満たして BCNF を満たさない形は、複数の複合候補キーが属性を共有する場合にしか現れず、大半のテーブルでは両者は一致します。また、BCNF への分解には代償もあります。分解すると、元のテーブルにあった一意性のルールが、分解後のどのテーブルの制約としても宣言できなくなる場合があるのです。これを、従属性の保存が破れると言います。

ここまでの正規形は関数従属だけを扱いました。関数従属がすべてキーに揃っていても、まだ残る冗長があります。あるエンティティについて、互いに独立に複数の値を持つ事実が二つ、一つのテーブルに同居する場合です。二つの多値の事実を同じテーブルの行で表すには、値の全組合せを並べるしかありません。すると片方に値を一つ追加するだけで、もう片方の値の数だけ行を挿入することになります。この関係を多値従属と呼び、第4正規形は、自明でない多値従属の決定項が候補キーを含むことを求めます。実務の指針としては、独立した多値の事実はテーブルを分けて持つ、と覚えれば違反のほとんどを防げます。第5正規形はさらに先の形で、二つへの分割では元に戻せず、三つ以上のテーブルへの分解によってのみ復元できる場合を扱いますが、そうした組合せの業務ルール自体がまれで、実務で意識する場面は少ないです。

後半のテーマ、非正規化に移ります。正規形を満たすテーブルは更新に安全ですが、読み出しには結合が要ります。非正規化は、冗長の再導入と引き換えに結合を減らす設計判断です。引き換えに戻ってくるのは更新異常のリスクですから、そのリスクを管理できる条件がそろっているかで判断します。条件は三つです。第一に、書き込みの経路が一つに制御されているか。元データから定期的に作り直される派生テーブルなら、混入した矛盾は次の再生成で消えます。第二に、読み取りが支配的か。冗長な列は書き込みのたびに複製のコストを生むので、書き込みが読み取りに比べて十分少ないことが前提です。第三に、矛盾を検出する検査を置けるか。崩した正規形が分かっていれば、破れうる従属も分かり、それを検査に翻訳できます。OLTP のテーブルは、複数の画面や API が直接書き込むため、一つ目の条件を満たしにくい。一方、DWH の変換パイプラインが作るテーブルは、三つの条件を典型的に満たします。第1章で述べた、OLTP は正規化、OLAP は非正規化という対比は、この条件の差の現れです。もう一つ、順序も判断のうちです。正規化された論理モデルを先に理解し、そこから意図して崩すのでなければ、どこに冗長があるかを列挙できず、検査の設計もできません。

ここからは具体例です。これまでの章では書籍オンラインストアの設計を整った形で組み上げてきましたが、本章では逆に、崩れた形から出発します。ストアの立ち上げ初期に、注文フォームの入力内容をそのまま一行ずつ保存していた、という状況を考えます。注文明細一件を一行とし、注文 ID と行番号の組を主キーに、注文日時、顧客 ID、顧客名、メールアドレス、書籍 ID、題名、著者名、数量、単価といった、関係する情報をすべて列に持つテーブルです。作為的な悪例に見えるかもしれませんが、スプレッドシートの台帳をそのままデータベースに移した場合などに、同じ形をよく見かけるでしょう。

この構造では、先ほどの三種類の異常がすべて起きます。ある顧客が氏名を変更すると、その顧客の明細行すべての顧客名を更新しなければならず、一部だけ更新すれば矛盾が残ります。これが修正異常です。新しい顧客を会員登録だけで記録するすべはなく、最初の注文が発生するまで顧客はどこにも存在しません。これが挿入異常です。ある書籍の唯一の明細を注文キャンセルで削除すると、その書籍の記録そのものが消えます。これが削除異常です。さらに著者名はカンマ区切りの複数値で、第1正規形にも違反しています。

分解の前に、このテーブルの関数従属を業務ルールから書き出します。注文 ID と行番号の組が決まれば、書籍 ID、数量、販売単価が決まります。注文 ID だけで、注文日時と顧客 ID が決まります。顧客 ID が決まれば顧客名とメールアドレスが、書籍 ID が決まれば題名、ISBN、定価、著者名が決まります。ここで販売単価の位置に注意してください。同じ単価という言葉でも、定価は書籍の事実として書籍 ID に従属し、販売単価は注文時点の価格という明細の事実として、キー全体に従属します。従属の引き方が業務ルールそのものであることが、この一列によく現れています。

分解は正規形の順に進みます。まず第1正規形として、カンマ区切りの著者名をほどきます。著者は注文についてではなく書籍についての事実なので、書籍の側に移します。移した先で書籍と著者は多対多になり、第2章で行った、著者テーブルと対応表への分解がそのまま使えます。次に第2正規形として、候補キーの一部分である注文 ID だけに従属する、注文日時と顧客の情報を、注文 ID を主キーとする注文テーブルへ移します。注文日時は明細ごとの事実ではないので、明細の行に置くかぎり、日時の訂正が明細の数だけの更新になってしまうからです。最後に第3正規形として、注文テーブルに残った、顧客 ID を経由して決まる顧客名とメールアドレスを顧客テーブルへ、明細に残った、書籍 ID を経由して決まる題名や定価を書籍テーブルへ移します。落ち着いた先は、顧客、注文、注文明細、書籍、著者、書籍著者の六つのテーブルで、これは第1章と第2章で組み上げた設計と同じです。偶然の一致ではありません。ER モデリングで属性を、それが表す対象のエンティティに置いていくと、事実の単位と行の単位が揃うため、結果はおおむね第3正規形に落ちるのです。正規化理論は、モデリングとは独立に同じ答えへ到達する検算の道具として使えます。

次に、第3正規形と BCNF の差が現れる例です。好みのジャンルについて相談できる、ジャンル別の案内担当を顧客に付けるサービスを考えます。業務ルールは二つ。顧客は一つのジャンルにつき一人の担当者を持ち、担当者は一つのジャンルだけを受け持ちます。これを顧客 ID、ジャンル、担当者 ID の三列を持つ一つのテーブルにすると、候補キーは、顧客 ID とジャンルの組と、顧客 ID と担当者 ID の組の二つになり、非キー属性が存在しないため、第3正規形までは自動的に満たします。しかし、担当者 ID が決まればジャンルが決まるという従属の決定項、担当者 ID は、どの候補キーも含みません。BCNF に違反するのです。実際に冗長は残っていて、担当者のジャンルは受け持つ顧客の数だけ重複して記録され、ジャンル替えは修正異常の温床になります。BCNF へ分解するなら、担当者とジャンルの対応表と、顧客と担当者の対応表の二つに分けます。ジャンルの重複はなくなりますが、代わりに、同じ顧客の同じジャンルに担当者は一人、というルールが、どちらのテーブルの一意性制約としても宣言できなくなります。これが従属性の保存の破れです。どちらを選ぶかは、どちらの事故が起きやすく、どちらを補いやすいかの比較になります。ジャンル替えが実際に起きる業務なら、分解した上で、失ったルールは二つのテーブルを結合して重複を数える検査で補います。ジャンル替えがない業務なら、元の形にとどまり、破れうる従属を検査で監視します。

第4正規形の違反は、書籍の販売条件で現れます。書籍ごとに販売地域が複数あり、販売フォーマットも複数あり、両者は独立に決まるとします。これを書籍 ID、地域、フォーマットの一つのテーブルに入れると、全組合せの行を並べることになります。たとえば日本とアメリカで紙と電子書籍を売っている書籍にオーディオブックを追加すると、地域の数だけ行を挿入しなければならず、日本の行だけを挿入すると、アメリカではオーディオブックを売らない、という意図しない主張が生まれてしまいます。分解は、事実ごとにテーブルを分けるだけです。書籍と地域の対応表、書籍とフォーマットの対応表の二つに割ります。ただし、この分解が正しいのは地域とフォーマットが独立な場合だけです。アメリカでは電子版しか販売しない、のように地域ごとにフォーマットが決まる業務ルールなら、多値従属は成立せず、三列のテーブルこそが正しい形です。多値従属もまた業務ルールの写しであり、分解の可否はデータの形ではなく業務ルールで決まります。

最後に、崩す側の例です。第1章で、分析用に結合済みのテーブルを dbt で作りました。題名を明細ごとに複製するこの構造は、本章の言葉で言えば、書籍 ID から題名への推移従属を意図的に再導入した、第3正規形違反です。判断基準に照らすと、このテーブルは三つの条件を満たします。書き込むのは dbt の変換処理だけで、実行のたびに元データから作り直され、利用は月次集計のような読み取りに限られます。そして、崩した従属が分かっているので、検査に翻訳できます。dbt では、違反行を返す SQL をテストとして置けます。このテーブルを書籍 ID でグループ化し、二種類以上の題名を持つ書籍 ID を返すクエリです。行が返ればテストの失敗として報告されるので、変換ロジックの誤りで矛盾した複製が生まれても、下流に届く前に検出できます。

この章のまとめです。正規化は、行の単位と事実の単位のずれが生む更新異常を、テーブルの分解によってなくす理論でした。分解の根拠となる関数従属や多値従属は、データの形ではなく業務ルールの写しです。正規形の系列は、繰り返しを禁じる第1正規形から、部分従属を外す第2正規形、推移従属を外す第3正規形、キー属性への従属も塞ぐ BCNF、独立した多値の事実を分ける第4正規形へと進みます。一方、非正規化は、書き込み経路の制御、読み取りの支配、検査の設置という三つの条件のもとで、冗長を承知で導入する設計判断です。正規形の知識は、守るときには分解の判定基準として、崩すときには検査すべき従属の一覧として働きます。以上で、第3章を終わります。
