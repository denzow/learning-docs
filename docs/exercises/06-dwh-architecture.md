# 第6章 演習問題

対象章：[第6章 DWH アーキテクチャ](../06-dwh-architecture.md)（[読み上げ原稿](../audio-scripts/06-dwh-architecture.md)）

## 問題

### 問1

Inmon はデータウェアハウスを、主題指向で、統合済みで、時系列で、不揮発なデータの集合と定義した。
この四つの性質の説明として正しいものはどれか。

- A. 主題指向とは、注文システムや倉庫システムといったソースシステムの単位でデータを編成することである
- B. 統合済みとは、ソースシステムごとに食い違う ID の体系やコードを、格納する前にそろえることである
- C. 時系列とは、過去の行を常に最新の値へ書き換え、現在の状態を正しく保つことである
- D. 不揮発とは、障害が起きてもデータが失われないように複製を保持することである

### 問2

部門ごとにソースシステムから直接データを抽出し、それぞれの変換でマートを作る構成を続けた結果、営業とマーケティングの売上の数字が合わなくなった。
章の説明に基づくと、この食い違いの根本的な原因はどれか。

- A. 部門ごとに抽出のタイミングが異なり、データの鮮度がずれるから
- B. 変換処理の実装にバグが混入し、それが検出されずに残るから
- C. 部門ごとに使う BI ツールが異なり、画面上の集計方法が統一できないから
- D. キャンセルの扱いや月の区切りといった指標を左右する決定が、マートの数だけ別々に下されるから

### 問3

Kimball のバスアーキテクチャは、正規化された中央の統合層を持たないにもかかわらず、マート間で数字の整合を保てるとされる。
それを可能にする仕組みはどれか。

- A. 複数のファクトテーブルが同じディメンションテーブルを共有し、顧客の区分や期間の区切りの定義がそこに一元化されるから
- B. すべてのビジネスプロセスを、単一の大きなスタースキーマに統合して管理するから
- C. ステージング領域を恒久的な統合層としてモデリングし、利用者に公開するから
- D. マートごとの集計結果を定期的に突き合わせ、差異を自動で補正する処理を設けるから

### 問4

dbt Labs が推奨する staging、intermediate、marts の三層構成は、章の見立てでは Inmon と Kimball の対比の中でどう位置づけられるか。

- A. Inmon 方式の実装であり、staging 層が正規化された EDW に相当する
- B. Kimball 方式の純粋な実装であり、Inmon 方式の要素は含まれない
- C. marts が Kimball のバスを実装しつつ、EDW が担っていた仕事の一部（ソース差異の吸収と履歴の獲得）を staging と snapshot が引き受けた混成である
- D. 独立データマートの現代版であり、層の構成は部門ごとに自由に決めてよいとされる

### 問5

書籍ごとに、注文された冊数と出荷された冊数を月別で並べたい。
注文と出荷はグレインの異なる別々のファクトテーブルに記録されている。
この問いに答える定石はどれか。

- A. 二つのファクトテーブルを、共通に持つ order_id で直接結合して集計する
- B. 各ファクトを共通のディメンション属性でそれぞれ集計し、その集計結果同士を突き合わせる
- C. 細かいほうのグレインに合わせて注文側の行を複製し、両者を一つのテーブルにまとめてから集計する
- D. 出荷ファクトテーブルに注文冊数のメジャーを追加し、単一のテーブルで完結させる

## 解答と解説

### 問1

**解答**：B

統合済みとは、ソースごとに食い違う ID の体系、コード、単位、表記を格納前にそろえる性質であり、B が正しい。
主題指向はアプリケーションの単位ではなく顧客や注文といった業務の主題の単位で編成することなので、A は逆である。
時系列は履歴の保持を指し、不揮発は追記と読み取りだけで運用し行を書き換えないことを指すから、C と D はどちらも定義と食い違う。
「データウェアハウスとデータマート」の節が扱った、Inmon の古典的定義の理解を問う問題である。

### 問2

**解答**：D

章は、独立データマートの食い違いを偶然のバグではなく構造から生まれるものと説明している。
キャンセルされた注文を数えるか、月の区切りを注文日と出荷日のどちらで取るかといった決定が、マートの数だけ別々に下されるからである。
A や C のような鮮度やツールの差も現場では起きうるが、それらを解消しても定義の決定が分かれている限り数字は合わないため、根本的な原因ではない。
Inmon と Kimball のどちらも、この定義の分裂を一度だけ行う場所を用意することで防ごうとした。

### 問3

**解答**：A

バスアーキテクチャでは、統合の仕事を適合ディメンションが引き受ける。
注文と出荷のファクトが同じ dim_customers や dim_date を参照していれば、どのマートでも顧客の区分と月の区切りが一致し、プロセスをまたいだ突き合わせが成り立つ。
共通の定義は中央の層ではなく共有されるディメンションそのものに宿る、というのが「Kimball のバスアーキテクチャ」の節の要点である。
C はステージングの位置づけと矛盾する（Kimball のステージングは利用者から見えない作業場であり、恒久的にモデリングされた層ではない）。

### 問4

**解答**：C

章は三層構成を、どちらか一方の純粋な採用ではなく混成として読んでいる。
marts はプロセス別のスタースキーマを適合ディメンションでつないだ Kimball のバスそのものであり、一方で EDW が一手に担っていたソース差異の吸収と履歴の獲得は staging と snapshot に移っている。
A が誤りなのは、staging がソースと 1 対 1 の整形の層であり、正規化された主題別の EDW ではないからである。
クラウド DWH では層を増やすコストが桁で下がり、要素を層として並べる形が実務の落とし所になった、というのが「現代の実務での混成」の節の説明である。

### 問5

**解答**：B

グレインの異なるファクト同士を扱う定石はドリルアクロスであり、各ファクトを共通のディメンション属性で集計してから結果同士を突き合わせる。
A のように直接結合すると、1 件の注文明細が分割出荷で複数の出荷明細に対応したとき、注文冊数が出荷明細の数だけ複製されて合計が水増しされる。
C も同じ複製をテーブルの中で起こすだけで、水増しの問題は解決しない。
そしてこの突き合わせが成り立つのは両側の集計キーが同じディメンションから来ているときに限られ、適合ディメンションの価値がここに現れる。
