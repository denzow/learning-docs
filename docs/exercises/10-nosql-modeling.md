# 第10章 演習問題

対象章：[第10章 NoSQL のデータモデリング](../10-nosql-modeling.md)（[読み上げ原稿](../audio-scripts/10-nosql-modeling.md)）

## 問題

### 問1

NoSQL のデータベースでアプリケーションのデータストアを設計するとき、最初に行う作業はどれか。

- A. 業務の事実を洗い出して正規化し、更新異常の起きない構造を先に固める。
- B. アプリケーションがデータに発行する問いを列挙し、それぞれを一回の取得で返せる形を考える。
- C. データ量の見積もりから、サーバの台数とデータの分割方法を先に決める。
- D. スキーマレスなので構造の設計は後回しにでき、実装を先に始めて構造は運用しながら決める。

### 問2

第8章の OBT やネスト構造も、問いの形に合わせてデータを畳んでおく操作だった。
NoSQL における畳み込みが第8章のそれと異なる点として適切なものはどれか。

- A. NoSQL の畳み込みは読み取りのためではなく、もっぱら書き込み性能のために行われる。
- B. NoSQL では畳み込みの同期を変換パイプラインが担うため、アプリケーションの負担は第8章より小さい。
- C. 第8章の畳み込みは一次データだったが、NoSQL の畳み込みは元のテーブルからいつでも作り直せる複製である。
- D. 第8章の畳み込みは元から作り直せる導出だったが、NoSQL の畳み込みは一次データであり、複製をそろえ続ける責務もアプリケーションのコードに移る。

### 問3

電子書籍ストアの注文文書には、明細として注文時点の書籍タイトルと単価が埋め込まれている。
書籍マスタで価格が改定されたとき、この埋め込んだ単価をどう扱うべきか。

- A. 書き換えない。注文時点の事実を写した複製であり、そもそも同期してはならない。
- B. 整合性を保つため、改定と同時にその書籍を含む全注文文書を更新する。
- C. 即時の更新は負荷が高いので、夜間バッチで全文書を走査して最新の単価にそろえる。
- D. 単価の複製をやめてマスタへの参照に変え、表示のたびに最新の価格を引く。

### 問4

読書進捗のワイドカラムテーブルは、顧客 ID と ISBN の組をパーティションキー、時刻の降順をクラスタリングキーとしている。
新たに「顧客ごとに、購入済みの書籍を最近読んだ順に並べる」という問いが加わったとき、ワイドカラムの流儀に沿った対応はどれか。

- A. クラスタリングキーに ISBN を加え、同じテーブルの並び替えだけで答える。
- B. パーティションキーを顧客 ID だけに変更し、既存の問いも含めて一つのテーブルで返す。
- C. 顧客 ID をパーティションキーとし最終閲覧時刻の降順を並びに持つ別テーブルを作り、進捗の書き込み時に両方へ書く。
- D. パーティションを横断する問い合わせを許す設定にし、実行時に全パーティションから集めて並べ替える。

### 問5

「更新が 30 日ないカートの一覧を出す」という週次の問いがある。
カートはキーバリューストアに置かれ、上書きされ、注文の確定や取りやめで削除される。
この問いへの答え方として、章の方針に合うものはどれか。

- A. 週次バッチで本番のキーバリューストアを全件走査し、更新時刻で絞り込む。
- B. 変更ストリームから変更と削除のイベントを取り込んでキーごとの版を追記で積み、DWH 側で最新版の更新時刻を条件に抽出する。
- C. カートをドキュメントデータベースに移し、更新時刻への索引を張って直接問い合わせる。
- D. カートの値に放置フラグを持たせ、30 日経過したらアプリケーションがフラグを立てて回る。

## 解答と解説

### 問1

**解答**：B

結合を持たない NoSQL では、問いの実行時にデータを組み立てるという手が使えないため、読みたい形をあらかじめ作って格納しておくしかない。
だから設計はアクセスパターン（アプリケーションが発行する問いの一覧）の列挙から始まり、構造はその後に決まる。
A は構造を先に決め、どの問いも結合で組み立てられるリレーショナルの手順である。
D については、スキーマレスでも構造の合意はアプリケーションのコードに残るため、設計が不要になるわけではない（「設計原則の転換」の節）。

### 問2

**解答**：D

第8章の OBT はスタースキーマから作り直せる導出であり、定義の置き場にはしないと確かめた。
対して NoSQL の畳み込みは一次データそのもので作り直す元がなく、複製の同期も変換パイプラインではなくアプリケーションのコードが負う。
C はこの関係を逆に述べている。
B は DWH 側の同期のやり方であり、NoSQL に持ち込むことはできない（「設計原則の転換」の節）。

### 問3

**解答**：A

注文明細の単価は「その時点の値」を写した複製であり、第5章で履歴として扱った時点の事実が、ここでは同期の要らない埋め込みとして現れている。
B や C のように最新値へそろえると、注文時にいくらで買ったかという事実が失われる。
D はマスタが改定されると過去の注文の表示額まで変わってしまい、注文の記録として成立しない。
複製を見たらまず同期の責務を考えるのが原則だが、この種の複製だけは例外である（「ドキュメント」の節と具体例の注文文書）。

### 問4

**解答**：C

既存テーブルのパーティションは顧客と書籍の組で切られているから、書籍を横断する並びはパーティションをまたいでしまい、このテーブルでは答えられない。
ワイドカラムの流儀は、問いごとに別の並びの別テーブルを用意し、書き込み時に両方へ書くことで、読みのたびの組み立てを書き込み時の複製で置き換える。
B のように一つのテーブルへ寄せると、今度は「この書籍の最新位置をパーティションの先頭 1 行で返す」という既存の問いの形が崩れる。
D は実行時の組み立てに戻る発想であり、低遅延の読みという要件に合わない（「ワイドカラム」の節と読書進捗の具体例）。

### 問5

**解答**：B

キーバリューストアはキー以外の手掛かりでは探せず、条件で絞る問いには全件走査しかない。
A はその走査を、低遅延の読み書きを担う本番ストアに負わせる点で不適であり、こうした条件と切り口の問いは分析基盤の仕事に仕分けるのが章の方針である。
またカートは上書きと削除で現在値しか残らないため、変更ストリーム（第5章の CDC に当たる）から版を追記で積んで履歴を組み立てる必要がある。
C は本番の主要な問い（丸ごと読み書き）に合っていた型の選定を、頻度の低い問いのために変えてしまう対応である（「キーバリュー」の節と「分析基盤への取り込み」）。
