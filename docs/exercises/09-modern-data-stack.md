# 第9章 演習問題

対象章：[第9章 現代のデータスタックでのモデリング](../09-modern-data-stack.md)（[読み上げ原稿](../audio-scripts/09-modern-data-stack.md)）

## 問題

### 問1

変換の順序は、かつての標準だった ETL から、クラウド DWH を中心とする構成では ELT へ入れ替わった。
この転換を合理的にした要因の説明として、章の内容に合うものはどれか。

- A. 変換サーバの性能が DWH に追いつかなくなり、SQL 以外の変換手段が実用にならなくなったから
- B. BI ツールが生データをそのまま受け取ることを前提とするようになったから
- C. 保存が安価になり計算が従量課金になった結果、生のままロードして DWH 内の SQL で変換するほうが合理的になったから
- D. ETL ツールでは変換の Git によるバージョン管理が技術的にできなかったから

### 問2

dbt の三層の規約は、どの種類の決定をどの層に書くかの線引きである。
staging 層に置いてよい決定はどれか。

- A. 複数の marts モデルから再利用される結合
- B. 列名や型の統一、コード値の読み替えといった、行を増減させない整形
- C. グレインを宣言したうえでの集約
- D. 利用者に提供する結合済みの一枚の組み立て

### 問3

章は、指標の定義はテーブルの列として保存できないと述べた。
その理由として正しいものはどれか。

- A. 指標の計算は複雑で、SQL の集計関数では表現しきれないから
- B. 指標はメジャーと同じものであり、すでにファクトテーブルの列として存在しているから
- C. 集計済みテーブルを増やすと DWH の保存コストが許容できなくなるから
- D. 指標の値は集計の切り口が決まって初めて定まり、その切り口は問いの側が選ぶため、あり得る組み合わせを提供側が列挙し尽くせないから

### 問4

第8章の OBT とセマンティックレイヤーの関係の説明として、章の内容に合うものはどれか。

- A. 役割が違うので併存する。OBT は結合済みの表という物を渡すので表を入力に要求する道具に効き、セマンティックレイヤーは問いのたびに SQL を生成するので指標の定義の一貫性に効く
- B. セマンティックレイヤーは OBT の発展形であり、導入すれば OBT は不要になる
- C. OBT はセマンティックレイヤーの実装方式の一つである
- D. どちらも指標の計算式を一元管理する仕組みなので、プロジェクトではどちらか一方を選んで採用する

### 問5

具体例では、stg_shipment_items に書かれていた stg_books との結合を、同じ SQL のまま int_shipment_items として intermediate へ移した。
この整理の目的として正しいものはどれか。

- A. staging のモデルに結合があると dbt の実行がエラーになるため
- B. 結合を含むモデルに stg_ の名が付いたままだと、stg_ はソースの 1 対 1 の写しであるという約束をモデル名から信じられなくなるため
- C. staging の view では結合の実行が遅いので、実体化の方式を変えて性能を上げるため
- D. 読み替えのロジックに誤りが見つかり、書き直す必要があったため

## 解答と解説

### 問1

**解答**：C

ETL が標準だった時代の前提は、DWH の計算資源が高価で、生データを置く容量も貴重だったことである。
クラウド DWH がこの前提を崩したため、先に生のままロードし、変換は DWH の中の SQL で行う ELT が合理的になった。
D の変換のコード化（Git、レビュー、CI）は ELT への転換がもたらした帰結であり、転換の要因ではない。
「現代のデータスタックと ELT」の節に対応する。

### 問2

**解答**：B

staging はソーステーブルと 1 対 1 に対応させ、行を増減させない整形（hard rule）だけを置く層である。
この 1 対 1 を守ることで、ソースの構造変更の影響を staging の中に堰き止められる。
A は intermediate、C と D は marts に置く決定であり、staging に持ち込むと層の線引きが壊れる。
「三層の規約」の節に対応する。

### 問3

**解答**：D

テーブルは一つのグレインを宣言して持つが、指標の値はどの切り口で集計するかが決まって初めて一つに定まる。
切り口の組み合わせごとの集計テーブルを提供側が用意し尽くすことはできないため、計算式は問い合わせの側に残り、問いの数だけ複製される。
B はメジャー（グレインを持つ行の上の値）と指標（メジャーを切り口で集計して初めて定まる値）の混同であり、章が最初に区別を求めた点である。
「テーブルに焼き込めない指標の定義」の節に対応する。

### 問4

**解答**：A

両者は、利用者に規約の知識（正しい結合、正しい集計）を求めずに済ませるという狙いでは重なるが、渡すものが違う。
OBT は表という物を渡すのでスプレッドシートや機械学習に効き、セマンティックレイヤーは宣言から SQL を生成するので指標の定義の一貫性に効く。
役割が違うから置き換えではなく併存になり、B や D のように一方を選ぶ関係にはならない。
「セマンティックレイヤー」の節の OBT との整理に対応する。

### 問5

**解答**：B

dbt は層を知らないため、staging に結合があっても実行は通る（A は誤り）。
移動の目的は、名前が約束を運ぶという規約の利得の回復であり、だからこそ SQL は変えずに置き場と名前だけを変えれば足りた。
数百枚に育ったプロジェクトでは読み手が全モデルの中身を確かめるわけにはいかず、接頭辞が約束を運ぶことは規約が規模に耐えるための条件である。
「規約に照らした点検」の節に対応する。
